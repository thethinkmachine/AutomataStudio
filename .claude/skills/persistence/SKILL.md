### Export / codegen

[js/export-core.js](js/export-core.js) normalizes `App` into a machine **IR** via `buildMachineIR()`. Everything downstream consumes only the IR: [js/export-formats.js](js/export-formats.js) (DOT, TikZ, tables, sample words) and [js/codegen.js](js/codegen.js) (JS/Python/Java in table/switch/class styles). Both register their targets into `ExportFormats` from [js/export-registry.js](js/export-registry.js); [js/export-ui.js](js/export-ui.js) owns the dialogs. Adding a target means adding a registry entry and an IR consumer, not touching `App`.

PNG export can embed the workspace JSON in the image; dropping that PNG back on the canvas restores it ([js/persistence.js](js/persistence.js) `handleFiles`). Persistence also covers IndexedDB autosave, `.json` save/load, base64url share links, and JFLAP import ([js/import-jflap.js](js/import-jflap.js)).

### The document, and what version it is

**A file, a share link, a PNG payload and an IndexedDB record all carry the same object**, so they all carry the same three fields, and every one of them goes through `migrateWorkspaceDoc` on the way in. `format` is what the thing *is*, so a JSON file that happens to have a `machine` key is not mistaken for one of ours. `schema` is the only field that gates behaviour. `app` is informational — it is what a bug report needs, and nothing branches on it, because a build number is not a schema and treating it as one is how you end up unable to ship a patch release.

**The problem it fixes is that the format was already on its fourth shape with no way to say so.** `blocks`, `scope`, `meta` and `grammar` all arrived as `d.x || []`, and the two machine-type corrections were inferred from content. That works — absence is a sound proxy for "written by an older build" — right up until absence is ambiguous, or until an *older* app opens a *newer* file, drops the fields it does not know, and writes the loss back on the next save. So `assertReadableSchema` refuses a document from the future outright, naming both versions and the build that wrote it.

Points worth keeping in mind:

- **`SCHEMA_VERSION` is bumped only when a reader written for the previous number would get the document *wrong*** — a field that changed meaning, a default that flipped, a shape that moved. Adding an optional field is not a bump; every reader in `persistence.js` already treats absence as a default.
- **`MIGRATIONS[n]` takes a document at schema n to n + 1**, in order, so a v0 file passes through every step and each step only knows about the change it is named for. They may mutate what they are handed: every caller parses fresh — a file, a link, a fetch, a storage record — so there is no shared object to scribble on, and deep-copying a thousand-state machine per load to avoid a hazard that does not exist would be a real cost for none.
- **`migrateWorkspaceDoc` is idempotent by construction**, because it stamps the current schema. That is what lets `loadData` run it as a backstop for the paths that skip `validateSchema` — examples, storage records, algorithm results — without double-applying it on the paths that do not. [tests/workspace-format.test.js](tests/workspace-format.test.js) pins that directly, and it is the assertion that would fail first if a migration were made to depend on being run once.
- **`normalizeMachineType` is deliberately not in the chain.** `TM` with a branching δ becomes `NDTM`, and the hidden `PDA` alias re-derives to `DPDA`/`NPDA` — but those are not corrections to an old format. A JFLAP import, a hand-edited file and an algorithm result can all produce a nondeterministic δ under a deterministic type name, and none of them has a version to key on. A migration may assume it runs once on the way up from a known shape; these have to hold every time, forever, which is a different contract and so a different function.
- **`APP_VERSION` moved to [js/state.js](js/state.js)** and is re-exported by `workspace.js`. The save format stamps it into every document, and `persistence.js` reaching into `workspace.js` for a `const` would be reading a binding across an import cycle — the one thing that throws rather than resolving late. A leaf has no such cycle to be caught in.

### Where a workspace is kept

**`workspaces` holds one record per tab, keyed by its id; `meta` holds the one record saying which tabs exist, in what order, which is active, and what the config is.** That split is the whole of the storage design, and the cost it removes is worth stating plainly.

Until database v3 there was a single record under `snapshots/'current'` carrying *every* workspace. So autosaving one dirty tab meant serialising all of them — `getBackupPayload` maps over the whole of `Workspaces` — writing the lot to IndexedDB, and then serialising them a second time for a **synchronous `localStorage.setItem` on the main thread**, into a ~5MB quota. Eight tabs open and the reader paid for eight machines, twice, every fifteen seconds, to record a change to one of them. That is the quota failure the notes around `stripTabForStorage` keep circling, and it was O(all tabs) for a change of size one. A save now writes the record that changed plus the small index.

Points worth keeping in mind:

- **The index is the authority, so the tab records are garbage-collected rather than deleted.** A tab closed while the app was shut, or a write that failed partway, leaves a record nothing points at. Rather than tracking deletions — one more thing for a crash to interrupt — `sweepOrphanRecords` drops what `order` does not name. That is the rule `stateIndex()` and `blockIsIntact()` already follow: validate on read, never rely on having been told.
- **No `await` sits inside a live transaction, and `txDone` attaches its handlers before the first one.** IndexedDB commits a transaction as soon as control returns to the event loop with no request outstanding, so an await in the middle can leave the writes after it throwing into a transaction that is already gone — and a completion handler attached afterwards **never fires at all**, which is a save that hangs rather than one that fails. The orphan sweep and the tab reads are therefore separate transactions from the writes and the index read. Within `readRecordLayout` every `get` is issued synchronously before the first await, because awaiting them one at a time would be a transaction per tab and boot latency proportional to how many are open.
- **localStorage came off the hot path, not out of the design.** It is still the entire backend when there is no IndexedDB, and still the last-resort copy written on the way out. What it is no longer is a mirror refreshed on every autosave and every tab click — it is refreshed at the two moments a reader would recognise as checkpoints, an explicit Save and `beforeunload`, so the stale-fallback window is bounded by something a person can reason about.
- **Tab operations are coalesced.** Creating, closing, renaming, reordering and switching all change the index and nothing else about the machine, and a bulk close calls `saveBackupChecked` once per tab. `persistTabState` collapses a burst: a request arriving while a write is in flight sets a flag and is served by one re-run afterwards, rather than opening eight overlapping transactions that all describe the same final state.
- **`saveBackupChecked` no longer returns a meaningful boolean.** The write is asynchronous and reports failure through the save indicator, which is how `saveWorkspace` has always reported. No caller ever branched on the old return value.
- **The v2 store is kept, read-only, as the migration source.** `readWorkspaceSnapshot` tries the record layout, then the legacy record, and tags which it found; `loadBackup` writes the records out immediately when the answer was not `records`, so the next boot is a cheap one. Migrating on *read* rather than on write is deliberate — a reader who opens the app and closes it again has lost nothing, and a migration that only runs when there is something to migrate cannot corrupt a fresh install. Deleting `snapshots` would mean a rollback to an older build finds no tabs at all.
- **A payload of `null` is never written.** `getBackupPayload` answers null when there is no active workspace to describe, and writing that put the string `"null"` where the reader's tabs were.

**The database is `automata-studio`, and the one it replaced is adopted rather than abandoned.** An IndexedDB database is identified by its *name*, so renaming it points the app at a fresh, empty one — every existing reader's workspaces **and their block library** become unreachable in a single release, and the app boots to an empty canvas with nothing to say about it. `electron/main.cjs` carries the same scar for `userData`, where this rename stranded every saved workspace because the migration looked for the wrong spelling and so never once fired. `adoptLegacyDatabases()` is that lesson applied on the way in: it copies every store from `automata-playground` the first time the new database is opened, and copies **nothing** if the new one already holds anything, because overwriting live work would be worse than not migrating at all. Three details are load-bearing — a database is detected with `open` at *no version* and `onupgradeneeded` as the "it did not exist" signal, since `databases()` is not everywhere and no test stub has it; one opened only to look inside is deleted again rather than left as litter; and the memo is on the **promise**, not a boolean, because `blocks-ui.js` opens this database too and can easily get there first, and two concurrent adoptions would race on the same stores.

[tests/persistence-roundtrip.test.js](tests/persistence-roundtrip.test.js) pins the one invariant the stage exists for — **autosaving one dirty tab writes one record and leaves its neighbours byte-identical** — plus the sweep, the coalescing, the v2 read-back, that autosave does not touch localStorage while an explicit Save does, that a refused write rejects rather than hanging, and that an empty save leaves a good backup alone. Its fake IndexedDB models named stores, `getAllKeys`/`delete`, and a transaction that completes **once** rather than once per write — the old fake completed per `put`, which is exactly what would let a layout writing several records at a time pass while being wrong.

### A workspace has a file

**`.automaton` is a name, not a format.** What a custom extension buys is an OS file association, an icon, a meaningful file-picker filter and a filename that says what is in it — and none of that needs a custom encoding. The file is the same JSON it always was, `.json` is accepted on import forever, and a binary format would cost exactly the diffability and hand-inspectability a teaching tool's files want most. `.excalidraw`, `.tldr`, `.drawio` and `.ipynb` all make the same trade; JFLAP's own `.jff` is XML.

**[js/file-host.js](js/file-host.js) is the only module that knows which host it is talking to**, and it imports nothing. Both halves of that matter. On the website there is no filesystem — a save is a Blob and an `<a download>`, an open is an `<input type=file>`, and neither has a path, so *"save the file I opened" cannot be expressed*. In Electron all of it is real, and until now the desktop build used none of it: it saved through the same download path as the website, which is why it had no Save As dialog of its own, no Ctrl+S that meant save, no double-click-to-open, no associations and no Recent Files. `will-download` in `electron/main.cjs` papered over the first of those by turning every download into a Save As prompt; the rest simply were not possible without a path. And it is a leaf because `electron-bridge.js` already imports `persistence.js`, so reaching for `isElectron` there would be reading a `const` across an import cycle — the one thing that throws rather than resolving late.

Points worth keeping in mind:

- **Every operation answers `{ok, …}` and every one has an answer for "there is no host."** The browser path is a result, never an exception being handled, so a caller reads the same in both builds.
- **A cancel is not a failure.** `{ok: false, canceled: true}` is the reader pressing Escape, and a status line reading "could not save" after they changed their mind is a bug they will believe. Only `saveDocumentAs` can be cancelled — `saveDocument` writing to a known path has no dialog, so anything but success there is real.
- **The path is a property of the tab, not of the app.** Tabs are independent documents, and `ws.filePath` rides in the tab record, so closing the app leaves Ctrl+S still meaning the file you were working on.
- **A document that failed to load never binds its path.** Binding it would point Save at a file the app could not read and overwrite it with something else. That is the one assertion in [tests/file-documents.test.js](tests/file-documents.test.js) worth reading first.
- **A drag-and-drop never binds a file either.** A dropped file has a name but no path — the browser does not give one and Electron removed `File.path` in v32 — so a drop loads the machine and leaves Ctrl+S meaning whatever it meant before, rather than silently retargeting it at a file the reader dragged in to look at.
- **`applyDocument` is the one parser**, shared by the drop handler, the hidden file input and the host. It branches on the *filename*, not on where the bytes came from, which is what lets a PNG arrive as an ArrayBuffer from a `FileReader` and as base64 over IPC and be read the same way. A PNG has to stay bytes: it carries the workspace in a trailing text chunk, and decoding it as UTF-8 first mangles everything before the marker.
- **The download is named after the workspace.** It was `automaton.json` every single time, so every save after the first landed as `automaton (1)`, `automaton (2)` — a folder of files none of which say what is in them.

**Three ways a file arrives from the OS, and they land at different moments.** macOS sends `open-file`, possibly *before* the window exists; Windows and Linux put the path in `process.argv`; and a second launch while one is running arrives through `second-instance`. `pendingOpenPath` bridges the timing — a path that arrives before the renderer is listening is held, and `file:take-pending` is how the renderer collects it once it is. **Without that collection, opening the app by double-clicking its own file type — the commonest way there is — shows an empty canvas.** The `open-file` handler is registered at module scope for the same reason: on macOS it can fire before `whenReady`, and a handler installed later misses the very event that launched the app.

**Collecting that path is only half of it: the renderer has to be ready to keep it.** `electron-bridge.js` subscribes at module scope and is imported *first* in `main.js`, so on a cold launch `file:take-pending` resolves while `init.js` has not run — and `loadBackup()` is an IndexedDB round trip that resolves later and ends in `switchTab`, which rehydrates `App` from the stored tab. The file loaded and was then painted over by whatever had been on the canvas last time. Which is exactly the shape the reader sees: double-clicking a `.automaton` while the app is *running* is fine, because there is nothing left to restore, and double-clicking one to *launch* it is not. So `openExternalDocument` holds a handed-over document until `markBootRestored()` is called at the end of `finishBoot`, after the restore and after the shared link. It is a queue rather than a single slot, because `second-instance` can deliver while the first launch is still booting.

**Opening a file never destroys the machine on the canvas — the tab is the document, so the rule is the one every tabbed editor uses.** `placeOpenedDocument` in [js/persistence.js](js/persistence.js): the file is already open in a tab → go to it; this tab is untouched → read it in; otherwise → open a tab for it. Three things make it hold.

- **"Untouched" is about content, not about the dirty flag.** A workspace restored from the backup is not dirty and is very much occupied, which is the case this exists for.
- **A tab that already carries a `filePath` is never reused, whatever is drawn on it.** That path is what Ctrl+S writes, so reusing the tab would silently retarget the reader's save at a different file.
- **Reading and placing are two steps, and the split is the whole reason `readDocumentPayload` exists.** A file that will not parse must leave the reader exactly where they were, with no empty tab to close — so nothing is created until the payload is known to read. `import-jflap.js` is split the same way (`readJFLAPText` / `importJFLAPData`) rather than being parsed twice.

Every way in goes through it: the Open dialog, a double-click, the hidden `<input type=file>` and a drop. A drop has a name and no path, so it still binds no file — but with the canvas occupied it now lands in a tab of its own like everything else, rather than replacing what is there.

**Save is one act, and it was two.** The header's floppy persisted the workspace record while Ctrl+S — the shortcut that button's own tooltip advertises — *also* wrote a file, which on the website meant a download. So pressing Ctrl+S on the site dropped a fresh copy into Downloads on every press, and clicking the button that says "Ctrl+S" produced no file at all. `saveNow()` is what both call now, and what the native File ▸ Save sends. The hosts still differ in what there is to save — the desktop writes the bound file (asking the first time) plus the record behind it; the website has no file to write, so Save is the workspace save and **Ctrl+Shift+S is what produces one** — but the button and the keystroke are never two different things.

**And the labels say which host this is**, written once at boot by `syncDocumentLabels()` rather than branched on at hover, since `hasFileHost()` cannot change during a session. A reader on the website told "Save workspace" goes looking in their Downloads folder, finds nothing, and concludes that saving is broken rather than that it saved somewhere else — while the one control that *does* write a file was a menu item called "Save Machine As…" inside a tray called "Export". On the website that item reads "Download Machine (.automaton)". The Open button's tooltip named PNG and JSON only, which is the app's own format missing from the list of things it can open.

**`requestSingleInstanceLock` is what makes `second-instance` exist at all**, and it is load-bearing beyond convenience: two instances sharing one `userData` directory is exactly how the version-bump deadlock `openWorkspaceDb` guards against happens in the wild.

### An exported diagram carries its own type

**An export used to carry font *names* and no fonts, and it failed twice over.** `buildExportSVG` inlines every rule it can reach from `document.styleSheets`, but the Google Fonts sheet is cross-origin, so `sheet.cssRules` throws and the `@font-face` rules land in the empty `catch`. And even with them, PNG could not have used them: `exportPNG` rasterises through `img.src = blob:`, and **an SVG loaded as an *image* fetches no external resources at all**. So a diagram opened anywhere without DM Sans and JetBrains Mono installed fell back to a generic face, at widths [js/geometry.js](js/geometry.js) never planned for — and because the dev machine has both fonts, this is invisible from the inside.

**[js/glyphs.js](js/glyphs.js) removes the dependency instead of working around it: a path needs no font.** It replaces each `<text>` in the clone with a `<g>` of `<use>` references into a `<defs>` glyph cache, which fixes both formats at once. It is also the *small* option, which is the part worth stating: an embedded subset of the families is ~120KB per export, where the outlines a diagram actually uses are ~15KB, because a machine reuses `q`, `0` and `1` far more than it introduces new characters — a 96-character diagram is 22 distinct glyphs, and the 23rd `q` costs a reference rather than an outline.

Two things make it cheap enough to do at all, and they are the whole design:

- **The outlines are extracted at build time.** `scripts/build-glyphs.mjs` (`npm run glyphs`, output committed, the arrangement `build-icons.mjs` already uses) is a TrueType reader — table directory, `cmap` formats 4 and 12, `glyf` including composites — that writes `js/glyphs/*.json`. Browsers expose **no glyph-outline API**, so the alternative is shipping a font parser (~180KB) plus binaries it can read, and it could not be the woff2 the page already loads, because woff2 is brotli. Here the parser is a script run by hand and what ships is a table of path strings, fetched only on export and only for the faces that export uses. Sources are Google Fonts' **v1** CSS API, which serves plain TrueType to a client that does not advertise woff2 — and with `&subset=`, or the default is latin-only and has none of the symbols the app draws.
- **Positions are measured, not computed.** `getStartPositionOfChar` reports where the browser actually put each character, so `text-anchor`, `dominant-baseline`, the em-relative `dy` stacking on multi-line labels, letter-spacing and kerning all come out right without this module knowing they exist. Re-deriving that layout would be a second implementation of text shaping that could disagree with the one on screen. Where there is no such API — the Node test DOM — every label stays text.

Points worth keeping in mind:

- **A label is converted completely or not at all.** Half a label in outlines and half in text would be worse than either, so a character with no outline anywhere leaves its whole element alone — and the *count of what was left* is what tells `exportPNG` it still needs a font. The same refusal covers a family with no table (better text than the wrong face) and a run whose white space SVG collapsed, where `getNumberOfChars()` disagrees with the string and every index after the collapse would name the wrong glyph.
- **The fallback is per character, and it is not optional.** JetBrains Mono has no `⊔`, `⊢` or `⊣` — the blank and both end markers in `App.config.sym`, i.e. the symbols on every tape machine the app can draw, which the browser is already substituting for today out of whatever the reader happens to have. `math-400` (Noto Sans Math, restricted to a listed ~90 symbols rather than the ranges they sit in, which would cost ~90KB to cover integrals nobody will draw) makes that substitution one known face instead of the reader's. Refusing the label instead would mean no Turing machine ever exports outlines.
- **Paint is resolved and written inline, never inherited.** `getComputedStyle` has already turned every theme variable into a literal, and the class is deliberately dropped: a rule from the scraped stylesheet would outrank a presentation attribute, and several canvas rules select the element *type* (`.edge-pill text { fill: … }`) and stop matching the moment the `<text>` is a `<g>`. The layout attributes are dropped for the opposite reason — the glyphs carry their own positions by then, so a stray `text-anchor` or `x` on the group would move every one of them. `clip-path` and `transform` are kept, being what holds a note's text inside its box and what the measured coordinates are relative to.
- **A halo is a separate pass, not a `paint-order` hint.** `.tlbl` paints one so an edge does not run through its own caption; applied per glyph it would lay each glyph's halo over the previous glyph's fill, so the run's halos are laid down as one group before any of its fills.
- **Weight past the heaviest master is stroked and italic is sheared**, because both are already synthetic on screen — `.state-sub` asks for 600 and `.priority-value` for 700 while JetBrains Mono is loaded at 300/400/500, and no italic is loaded at all. Reaching for a different family instead would change the letterforms rather than their weight.
- **Relative path commands, and every pair in one command shares an origin.** That is not a style preference: the deltas are most of the file, and *chaining* the pairs of a `q` — advancing the current point between the control point and the end point — puts the end of every curve out by the control point's offset. Straight-line glyphs come out perfect either way, so the damage looks selective and reads as a font problem. `contoursToPath` now decodes what it just wrote, against the spec rather than against itself, and throws if the points disagree.
- **[js/export-fonts.js](js/export-fonts.js) is the backstop, and it is offered to PNG only.** The rules are consumed while the image is being rasterised and never reach the `.png`, so correct glyphs cost the image nothing; in an `.svg` the same base64 would sit there permanently, which is the cost the outlines exist to avoid. It re-fetches what the stylesheet scrape cannot reach and inlines it as `data:` — both Google endpoints send `Access-Control-Allow-Origin: *`, and the browser has already downloaded those exact files to render the page.

**The one structural constraint is that `withFullRender` restores in a `finally`.** Measuring has to happen inside it — a cropped export frames the *machine*, and on a windowed canvas both the crop box and the character positions would otherwise see only what was on screen — but the glyph tables are *fetched*, and an async callback would hand `withFullRender` a promise it never waits for, putting the window back before the work that needed it had run. So `buildExportSVG` is three phases around one await: `stageExportSVG` clones, plans and crops synchronously inside the full render; the tables load outside it; `finishExportSVG` applies to a clone nothing is measuring any more. **Planning happens before the clone is edited**, because the plan pairs the two trees' `<text>` elements by index — `applyOutlines` then skips a planned element that the notes/dividers exclusion went on to drop.

The tables are runtime assets like `js/examples/*.json`, copied verbatim by the Vite plugin and deliberately not imported: a static import would put ~330KB into the single bundle for something only an export reads. Nothing here is reached from an `on*` attribute, so neither module adds a name to `bridge.js`.

**Worth knowing separately: the scraped stylesheet dwarfs everything else in an export.** A three-state diagram measures ~334KB, of which the outlines are 17KB, the diagram itself 6KB, and **312KB is `cssRules` — the entire application stylesheet**, modals, panels and StateMate included, inlined into every image. Narrowing that scrape to the canvas rules is the single largest size win available here and is untouched.

**A share link is DEFLATEd, and the mark is what makes that a change rather than a break.** The payload is a whole workspace — the same two dozen key names once per state and once per transition — and then base64 on top, which costs a third more again on a file that is mostly repetition: a 300-state machine was a 60KB URL and a 1000-state one 200KB. The hash never reaches a server, so nothing refuses it outright; what happens instead is that some client between the two people *truncates* it, and a truncated payload decodes to nothing. Compressed, those two are 7.8KB and 30KB.

Three things hold it together. **`SHARE_COMPRESSED_MARK` (`z.`) carries a character base64url does not**, so a link written before this existed can never be mistaken for a compressed one and every one of them still opens — `decodeSharePayload` is the single reader for both generations. **Compressing is best-effort**: `CompressionStream` is asynchronous and not everywhere, and `compressToB64Url` answers `null` rather than throwing, so a browser without it falls through to the old encoding — an uncompressed link is a longer link, never a broken one. And **`copyShareableLink` has to keep the clipboard grant**, because compressing puts a tick between the click and the write and Safari grants the clipboard only inside the gesture that asked for it: `write()` is handed a *promise* of the text where `ClipboardItem` allows it, with `writeText` and then the prompt behind that.

`getShareableLink` and `loadSharedLinkFromURL` are async for it, which is why `finishBoot` awaits — it already ran off a promise, so the import costs the boot nothing it was not already paying. [tests/share-link.test.js](tests/share-link.test.js) pins the round trip, the legacy link, the ratio, and that a truncated link is refused rather than half-imported.

**And the file rounds its geometry, which is worth about as much again.** A coordinate is a float the moment a state has been dragged — `100.35847091674805` is eighteen characters written twice per state — and on a diagram of any size the file is mostly coordinates, so `SAVE_PRECISION` in [js/persistence.js](js/persistence.js) takes them to whole pixels: a 300-state link goes 18KB → 8.9KB, roughly doubling what DEFLATE already bought. Only `loopAngle` and the camera's zoom keep decimals, because a whole number of radians is a quarter turn.

Two things make that safe. It happens **on the way out and never on `App`** — `roundForSave` copies rather than edits — because rounding a state as it is dragged would quantise the drag, and the layout passes iterate on their own output, where the error accumulates into a visible drift. And **`exportWorkspaceState` deliberately does not do it**, which is the line between the two serializers: a file is a published artifact and half a pixel is nothing in one, while a tab switch and an undo have to give back exactly the machine that was there.

### JFLAP import

The reader is hand-rolled rather than `DOMParser`-based — `.jff` is machine-written and regular enough that a focused reader covers it and stays testable without a DOM. `<type>` names a *family*, so the specific machine type is read back off the transitions by `jflapMachineType` the same way `loadData()` does for the app's own files.

**JFLAP 6.1 added a notation 4.x has no equivalent for, and reading it literally fails silently.** A `<read>` may name a set of symbols bound to a variable — `y, a } w` — with `<write>w</write>` meaning "put back whatever you just read", so one edge stands for one transition per listed symbol. Read as a plain symbol it becomes an eight-character tape symbol no cell can ever hold: the edge draws, Σ and Γ fill with garbage, and the machine rejects everything with no error anywhere. `jflapParseRead` classifies the three forms and the transition loop `flatMap`s a set into one transition per symbol; **the negated form `! a, b } w` cannot be expanded inline** because it subtracts from an alphabet that is not complete until every transition has been read, so it is parked in `deferred` and resolved in a second pass.

Points worth keeping in mind:

- **A `<push>` string is characters, not a symbol.** JFLAP stack symbols are single characters and `AZ` pushes A then Z; putting `"AZ"` in Γ adds a symbol nothing can match. `addStackSymbols` is the one place that decides this.
- **`<tapes>` has to be read before `jflapMachineType`**, or a 3-tape file whose transitions only touch 2 classifies as a single-tape `TM`. The widest transition is a lower bound on the tape count, never the answer.
- **A block's interior is a *reference*, not containment, and reading it as containment finds nothing.** `<block>` carries a `<tag>`, and the interior is a separate element named by that tag — which means two blocks may share one interior, this app's "two placements of one definition are two copies" arriving from the other direction. **Where that element sits differs between writers and neither is a superset of the other**: 6.1 appends it *inside* `<automaton>`, after the transitions under a "list of automata" comment, while jflap-lib's `createAutomatonElement` appends it to the **document element** beside `<automaton>`. `blockAutomaton()` searches both, nearest scope first, and accepts the nested shapes too. Getting this wrong is not a partial failure: every one of jflap.org's own samples finds no interior and degrades to plain states. A tag naming nothing is the 4.x arrangement, where the interior lived in a separate `.jff` the file only points at — there is nothing to expand, so it falls back to a plain state.
- **`~` is the wildcard and `!A` is a negation, and both read literally are tape symbols no cell can ever hold.** `~` is `sym.any`, which [js/machines/turing.js](js/machines/turing.js) already reads as "any symbol" and, as a write, as "put back what you read" — the same claim in a different glyph, so `jflapTapeSymbol` is the one place that translates it (and `□`, where JFLAP spells the blank out rather than writing an empty element). The bare `!A` is the braced `! a, b } w` form with nothing bound, so `jflapParseRead` returns it as a negation and the existing second pass subtracts it from Σ once the alphabet is complete; what says the symbol is put back is then the wildcard *write*, since there is no variable to name. Both are all over the 6.1 samples, and neither fails loudly — the edge draws, Γ gains a stray `~` or `!A`, and the machine matches nothing.
- **A JFLAP block is a node the size of a state, and here it is a box — so the layout has to be made room in.** 165×112 against a radius of 30 is four times the footprint, so a file that read perfectly well in JFLAP arrives with its boxes touching, the edges between them hidden underneath and their labels with nowhere to go. `spreadForBlocks()` answers with a **uniform scale, not a shove**: these files are drawn by hand in rows that mean something, and scaling keeps the author's layout exactly while giving every node the room its drawn size needs — pushing nodes apart pairwise turns a tidy row of eleven blocks into a scatter. Three things it has to get right. The separation is judged as **rectangles, clearing on either axis**, deliberately not by the circumscribed radius the routing passes use: judged as circles, two wide boxes side by side are "clear" with 34px between them, which is the gap an edge label disappears into. Nodes are grouped by **what they are drawn beside** — a state with its container's members, a box with its parent's — since two nodes in different scopes are never on screen together. And it is gated on the file having a block at all, so an import with no boxes keeps the author's coordinates untouched. `resolveNodeOverlaps` still runs after it, for the pair a scale cannot separate.
- **And the move has to be announced.** `loadData` emits `Change.GRAPH` itself, so the render that drew the boxes saw the file's *original* coordinates; without an `emit` after the spread the diagram on screen is the one from before it — boxes at their old positions, and every block's preview drawn for a box that is no longer there, which reads as previews that simply do not appear on first load.
- **An edge between blocks is `<transition block="true">` carrying a `<read>` and nothing else** in the 4.x style: JFLAP leaves a block on a symbol without writing or moving, which is the `Σ / Σ, S` exit edge said the other way round, so it is read as a tape transition writing back what it read. Read as a finite-automaton edge it would arrive on a Turing machine with no write and no direction. 6.1 writes full tape transitions instead, so both are accepted.
- **A `<block>` is this app's building block seen from the other side, so it is expanded rather than dropped.** JFLAP's block is an interior automaton entered at its own start state and left from the states it halts in, which is exactly what [js/blocks.js](js/blocks.js) means by an entry and its default exits — so `parseJflapLevel` recurses into the interior, gives every state a `blockId` and the instance's name as a prefix, and emits the same `blocks` records `inlineBlock` would. The machine that comes out is **flat**, so no simulator, decider or exporter learns anything new. Four things it has to get right: an edge *into* the block lands on its `entry`, an edge *out of* it becomes one edge per exit (JFLAP has one implicit exit — reaching any final state hands control on — and this app has one per halting state, so the expansion is what keeps the two saying the same thing); `<initial/>` and `<final/>` on the block itself are facts about it as an *outer* node, so they travel as the entry and as the exits joining F, while every other interior accept mark is dropped the way `inlineBlock` drops them; a block whose interior the file omitted still imports as a plain state, because an edge naming it has to stay resolvable; and a family with no stay move cannot have blocks at all (`machineSupportsBlocks`), where the grouping is dropped and **not one state, transition or verdict with it** — which is only safe because inlining is the semantics.
- **What could not be converted is reported, never dropped quietly.** `jflapToWorkspace` returns a `warnings` array — an expanded variable edge, an expanded block, a second `<initial/>`, a PDA whose empty-stack acceptance the app does not model — and `importJFLAPText` writes it to the machine card rather than the status bar, which holds one line for 2.5 seconds. These are caveats the reader has to weigh against the diagram, so they have to still be there a minute later. `warnings` is not part of the save format; `getWorkspaceData` is an allow-list and drops it.
- **Structures with no `<automaton>` each name themselves** (`UNSUPPORTED_TYPES`) — "no `<automaton>` element" tells someone who exported a regular expression nothing.

**JFLAP's tape is two-way infinite, unconditionally, for every Turing machine it writes.** That is a fact about the file rather than a guess about the machine in it, so `jflapToWorkspace` returns `twoWayTape: true` and `loadData` applies it — there is nothing to detect from the transitions and no machine type to pick. See [the tape](#the-tape) for why that is a setting rather than a family of extra machine types.
