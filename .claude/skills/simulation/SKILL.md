### Simulation

[js/simulation.js](js/simulation.js) is now the **player** — what a *run* is, rather than what a machine is. It owns the run box, the trace log, the step tracker, the scrubber, playback and the batch tester, and nothing about any particular machine. `runSim()` is four lines of dispatch: parse the input the way this machine reads input, run this machine's guards, record what the canvas highlights against, hand the result to this machine's simulator.

All simulators produce the same artifact: a flat `App.simSteps` array the UI scrubs with `App.simIdx`. Nondeterministic machines explore first (`exploreNPDA`, `explore2NFA`) then linearize the winning path with `traceSearchPath`. Step budgets are in `App.config` (`maxPdaSteps`, `maxTmSteps`, `langStepBudget`).

**That array is now a *prefix*, and how much of it exists is a setting.** The app used to precompute a whole run and then visualize it — fine for a DFA, whose run is `|w|+1` steps, and it is what froze the tab on a Turing machine, whose run is `maxTmSteps` steps each carrying a tape snapshot, all ten thousand built before the first frame. [js/machines/run.js](js/machines/run.js) is the cursor that replaces it: `makeRun(source)` over a generator or a finished array, with `steps` the same object for the life of the run — which is why every reader of `App.simSteps` (the log's tail, `trailUpTo`, the minimap, StateMate's trace tool) is untouched by the change. It simply grows now instead of arriving complete.

- **Two producers, and the player cannot tell them apart.** A machine that declares `stream` in its definition builds one step per iteration and hands them over as they are computed — the tape machines, the finite automata, Moore and Mealy. A machine that declares none is search-based: `simNPDA`, `sim2NFA`, `simFST`, the ω-automata and `simPDA` explore the configuration space and only then linearize the winning path with `traceSearchPath`, so **no prefix of their trace exists until the search has finished**. `streamMachine()` in [js/machines/index.js](js/machines/index.js) collects those with the paint suppressed and wraps the finished array in the same cursor. That is the honest shape of the computation, not a fallback.
- **The eager wrapper is what kept the port cheap.** Each generator has a one-line sibling (`simTM(tokens)` → `playEagerly(streamTM(tokens))`) so the old name still means what it always meant: run the whole thing, write `App.simSteps`, paint. Roughly forty call sites — the tests, StateMate, every direct caller — did not move. `playEagerly` carries the generator's *return* value, because `simNDTM` and the explorers answer with run statistics their callers read.
- **The mechanical edit was the push-then-stamp pattern.** These loops used to push a step and then reach back into `App.simSteps[length - 1]` to mark it accept/reject/loop. A step is now built as a local, decided, and only then yielded — whether it is the last one is not known until the transition has been looked for. Where the *budget* runs out the last step is marked in place after it was handed over, which is sound because the player holds the same object.
- **Suppression moved to [js/machines/paint.js](js/machines/paint.js)**, since `streamMachine` needs it and must not import the player. `runQuietly` survives as a delegate — two counters for one property would be two ways for a run to be half-silenced — and `renderSimStep` in `simulation.js` checks `isPainterSuppressed()` too, because the player calls it directly rather than through the hook.
- **Playback drives the computation.** `stepFwd` pulls, so the pull *is* the bounds check, and the autoplay tick advances the machine one step because the animation asked for it. `stepToEnd` becomes a computation rather than an index: it drains in `DRAIN_SLICE` slices with the page given back between them, or "go to the end" on a machine that never halts holds the main thread for its whole budget and takes the Escape key with it.
- **Three things stopped meaning "the total".** The step counter reads `4 / 128+` until the cursor is done, since the length of a streaming run is not knowable; `canResumeSim` gates on `runIsComplete()`, because sitting at the frontier of an unfinished run is a resumable position where sitting on the last step of a finished one is not; and the scrubber addresses the prefix, its `max` moving with it.

**The run button plays, pauses, resumes and replays — one control, four jobs.** Its not-playing branch used to call `runSim()` whatever the state, and `runSim()` begins with `resetSim()`: pausing to look at a configuration and pressing play again threw the run away and re-ran it from step 0, which is the one thing a pause button must not do, and it made pausing useless on exactly the runs worth pausing. Resuming is not a new capability either — the step-forward button already advances the same paused run without re-simulating; `canResumeSim()` is only what decides which of the two a press means. Two cases deliberately do *not* resume: a run sitting on its last step has nothing to resume and the button is already showing the replay icon by then, and a run whose word no longer matches the run box re-runs, because editing the box and pressing play means "run this". **`App.simInput` is what makes the second test possible** — the word the steps in `App.simSteps` were produced from, written after the guards so a refused run leaves nothing to resume into, and cleared by `resetSim` along with the steps.

### Running one block

[js/run-scope.js](js/run-scope.js). **Drilling into a block used to change what you could see and nothing about what you could do.** `runSim` reads `App.startId` and the whole flat δ; the word `scope` appeared in [js/simulation.js](js/simulation.js) exactly once, in the trail cache's key. So pressing play inside `CPU/ALU/add` ran the CPU, and if control never reached the adder on that word you learned nothing about the adder. There was no toggle.

**"Run this block on its own" and "run the whole machine but stop when it reaches this block" look like two features and are one** — a *run boundary*, a block whose subtree the player watches the run against. `subject` starts at that block's entry and stops when control leaves; `break` runs everything and pauses where control first enters. Both are answered by the same test on the same step, which is why they are one module rather than two passes over the same trace.

Points worth keeping in mind:

- **A boundary is enforced by the player, never by the machine layer.** Teaching twenty-five simulators to halt at a subtree would be twenty-five ways to disagree; the player already holds a cursor over the steps and already decides which one is on screen, so "do not go past this one" is a bound on the cursor. `stepAt` is the single gate — it was already the bounds check, so `stepFwd`, `stepToEnd` and the autoplay tick need nothing taught about it — and on a streaming run the steps past the boundary are never computed, because nothing pulls them. [tests/block-run.test.js](tests/block-run.test.js) pins the invariant that makes it safe: **a block run is step-for-step the whole-machine run from that point.**
- **The scan reads the steps array and never pulls, which is the one thing here that is easy to get catastrophically wrong.** "How far may the reader go" is asked on every render, and answered by walking the *cursor* it would materialize every step of the run on the first frame — draining a streaming machine to `maxTmSteps`, which is exactly the frozen tab [lazy execution](#which-kind-of-execution) exists to prevent. `scanBoundary` therefore inspects `steps` directly, with a cursor keyed on the array, so a run is walked once across every ask rather than once per ask.
- **`maxReachable()` is what an eager run needs, and it costs nothing when there is no boundary.** An eager simulator writes the whole trace before anything pulls a cursor over it, so there would otherwise be nothing to notice that control had left; the walk runs only when a subject or a break scope is set, and answers the array's end immediately otherwise. The scrubber's `max` and the step counter read the reachable prefix, or a block run's slider would reach into the host machine.
- **The one thing the machine layer reads is where to *start*, and that is now one declaration.** `runStartId()` in [js/state.js](js/state.js) answers `App.simStart || App.startId`, and `App.startId` stays exactly the machine's start: it draws the start arrow, it is q₀ in the formal definition, and it is what every exporter writes. A parameter threaded through the twenty-five reads would be twenty-four passing it on and one quietly deciding from the wrong state, so the test asserts against the source that `App.startId` appears nowhere under `js/machines/`.
- **The subject scopes the *player*, and deciding is a different question.** `decideMachine()` and `decideWord()` in [js/machines/index.js](js/machines/index.js) lift the override for the length of the call, so the Test Words table, the Language panel's fingerprint and StateMate's verification all answer about the machine. Left through, picking a block in the run box silently re-decided every one of them from that block's entry — a word flipping from reject to accept with nothing anywhere saying why. It is wrong rather than merely surprising, for two reasons that are the same reason twice: **a block has no F**, which is the whole point of the bullet below, so accept/reject measured from its entry against the host's F answers no question at all; and the Language panel prints Q, q₀ and F of the *machine* directly above the grid it would have scoped, so one panel came to contradict its own heading. `simStart` therefore does **not** ride in `snapshotMachine()` — a worker only ever decides, and its absence is what keeps the worker's verdict and the main thread's the same one.
- **A block has no verdict, so it does not borrow one.** Its accepting marks are dropped when it is inlined — a block finishing is not the machine accepting — so the answer is **which exit control left by**, which is what `block.exits` declares and what everything downstream of it branches on. An *undeclared* way out is reported as one rather than rounded to the nearest label: it is a real result, and it is also exactly what stops the block being reusable. A run that never leaves says that instead, since a caller downstream could wait on it forever.
- **The subject survives a reset; it does not survive the machine.** `resetSim` clears where the last run stopped and keeps what it was *about*, because re-picking the block for every word tried is the one thing you do repeatedly here. `clearTransientPointers` drops it, which is where the pointers that would outlive what they point at already go.
- **Changing the subject takes the run with it, and that is not tidiness.** A finished whole-machine run — one that went through the block and out the far side to an accepting state — was relabelled the moment the reader picked that block: ACCEPT became "No exit, control never left B", which is false about the very trace still drawn under it. It could not correct itself either, because `scanBoundary` is a cursor over an array it had already walked to the end. So `setRunSubjectFromUI` and `setBreakScopeFromUI` call `resetSim()` when the answer actually changed — steps produced from another start state, judged against another boundary, are not steps this question has an answer for.
- **The frame after the last one is the one that knows how the run ended.** The step where control leaves is materialized inside `stepAt` and then *refused*, so `App.simExit` is written after the last frame was painted; a streaming run learns it is `done` the same way, on the pull that fails. `stepFwd` redraws when either becomes true, and until either does a block run's banner shows nothing — on a streaming run the newest step always satisfies `isLast`, so where an ordinary machine falls through to a hidden banner this branch drew one, and "No exit — control never left B" flashed past on every frame of a run still inside the block and about to leave it. ⏭ escaped both, because it re-reads `maxReachable()` after every drain slice; play and step-forward, the two controls anyone actually uses, did not.
- **All of it is session state and reaches no serializer.** `runSubject`, `simStart`, `simBreakAt`, `simStopAt` and `simExit` are a property of this reader's investigation, not of the machine — the same reasoning [js/scope.js](js/scope.js) gives for the per-scope cameras. A file recording a start state that is not the machine's start would be a file that lies.
- **One `advanceOne()`, because there were three.** The autoplay tick was written out in `toggleAuto`, in `restartAutoTimerIfPlaying` and in the drain; two lines duplicated three ways is fine until something has to be added to all of them.
- **"Break in" is offered only while the subject is the machine.** Asking to stop on entering the block you are already starting inside is a question with no answer, and selecting a block is the other way of asking the same thing. The picker offers the machine and every block the reader is standing inside, outermost first — deliberately not every block in the machine, which is the Blocks panel's job.

### The trace log

**Its own card, and the rest of the run reachable from it.**

A transport you operate and a history you read are two things, and they shared one box: reading back through a run pushed the play button off the top of the panel, and collapsing the transport took the log with it. They are also the two sections most worth pulling into windows *separately*, which [js/panel-sections.js](js/panel-sections.js) can only offer per card. `rp-trace` is that card; `rp-simulate` keeps the tracker as its own elastic region.

**Only the tail is written, and that is not an optimisation.** The log used to be rebuilt from step 0 on every tick — quadratic in the length of the run, and the reason playing back a Turing machine got slower the longer it ran: at `maxTmSteps` a single tick meant building and parsing ten thousand divs, ten thousand times over.

But *"the rest is gone"* is a different claim from *"the rest is not drawn"*, and the elided line made the first one — a count, and no way to reach what it counted. The steps are all still in `App.simSteps`; the only reason they are not on screen is that drawing them costs. So the floor is lowered on demand: the line is a button, and reaching the top of the log pulls the next page in behind it.

- **An expansion lasts only while the cursor is still.** That is the whole of what keeps the quadratic from coming back. Every path that moves the playhead — a tick, a step, a scrub, a reset — calls `resetTraceWindow()`, because a reader watching playback is not reading history, and re-rendering a thousand revealed rows per tick is exactly the cost the tail exists to avoid. Reading history happens while paused, and there the render is one click.
- **A reveal holds the reader where they were.** The rows arrive *above* what is in view, so the content moves down by exactly the height added; without that, revealing a page throws them to the top of the page they have already read.
- **The button and the scroll both exist because either alone is wrong** — a button nobody sees at the top of a scroller is a dead end, and an auto-load with nothing naming it reads as the page jumping. The button is `position: sticky` for the same reason: it is the way *up* out of a scroller.
- **The header counts the prefix the reader can reach, not the array.** On a block run the steps past the boundary have been computed and belong to the host machine, so counting them had the Trace header say 6 over a scrubber reading `4 / 4`. `reachableCount()` is the one declaration the header, the scrubber and the step counter all read.
- `logFloor` is module state, so [tests/harness.js](tests/harness.js) clears it in `resetModuleState()` — a test that revealed a page would otherwise hand the next one a log already whole. Every path that moves the playhead goes through `handMovedPlayhead()`, which drops the window back to the tail **and** spends a pending break mark — a reader who has stepped past where control entered the watched block has already seen it, so pressing play afterwards must carry straight on rather than pause again on a mark it can no longer reach.

### Which kind of execution

**The trigger is run length, not machine size, and that is why this is not another thing `largeMachineProfile()` turns off.** The two are close to uncorrelated: a 1000-state DFA on a twelve-symbol word is thirteen steps and precomputing it is free, while a three-state Turing machine is `maxTmSteps` steps each carrying a tape snapshot, and it is that one which freezes the tab. Keying this on states-and-transitions would switch strategy on precisely the machines that never needed it.

So it is projected instead, from the machine's own mechanism and the length of the word — both known before the run starts. `projectedRunSteps()` in [js/state.js](js/state.js) answers `maxTmSteps` for a tape machine, `maxPdaSteps` for a stack machine, `|w| × |Q|` for a two-way head and `|w| + 1` otherwise; past `LAZY_STEP_THRESHOLD` the run streams.

- **`App.config.execMode` is `auto` | `eager` | `lazy`, and absent reads as `auto`** — the rule the render flags follow, so a settings profile written before this existed does not load pinned to one strategy. Settings → Workspace → Execution, beside Playback Speed, because it is a playback property.
- **Auto biases toward streaming when uncertain**, since the two mistakes are not the same size: streaming a short run costs a few microseconds of generator overhead, while precomputing a long one is the frozen tab this exists to prevent.
- **It is a policy; capability is the run's own answer.** `runsLazily()` says what should happen and `run.streaming` says what can — a search-based simulator arrives complete whatever is set, and the counter showing a true total is the honest report of that.
- **`hasExpensiveRuns()` is derived from the capability flags, not listed by name.** It replaced a private `EXPENSIVE` set of type names in [js/parallel/pool.js](js/parallel/pool.js), which a machine added to `MachineTypes` falls silently out of — no parallelism for a batch, no streaming for a run, nothing raised. Both callers now read one declaration: "is one word's work worth a worker" and "is this run worth streaming" are the same fact about the machine.
- **It rides the settings profile and never the workspace.** `detectLoops` and `twoWayTape` are in `getWorkspaceData()`'s allow-list because they change what a run *decides*, and a file that decides differently for the next reader is a file that lies. This changes only *when* the steps are computed — the verdict is identical, and the batch tester and Language panel go through `decide()`, which it never touches — so it stays in `getEditorSettingsData()`. The one thing it does change is that a streamed run's accept/reject banner arrives when playback reaches the end rather than immediately, which the tooltip says out loud.
- **A reader whose counter shows a `+` is owed the reason**, so the auto path prints one line into the trace log naming the budget. It is re-emitted by every log render rather than written once, because `renderSimStep` rewrites the log wholesale on every tick — a note inserted at the top would vanish on the next step. Only auto narrates: a mode the reader chose needs no explanation.

[tests/lazy-execution.test.js](tests/lazy-execution.test.js) pins the invariant everything else rests on — **a streamed run is step-for-step the run that was precomputed** — plus that a step is computed only when asked for, that the projection ignores machine size, that an explicit mode overrides it both ways, that the expensive-run judgement covers every tape and stack machine in the table without naming one, and that `execMode` reaches no workspace.

**Loop detection is what turns "would run forever" into a decision**, and `App.config.detectLoops` is the switch for it. A deterministic tape machine that revisits a configuration will revisit it forever, so `makeLoopTracker()` stops playback there and `markLoopStep` reports a *proven* non-halt — strictly more than the step budget can tell you, which is why it is on by default. Switching it off is a playback choice: the machine runs to `maxTmSteps` and `markTimeoutStep` reports **no verdict**, never a rejection. You switch it off to *watch* a machine not halt.

Three things keep that honest. **The setting acts inside `makeLoopTracker()` (in [js/machines/runtime.js](js/machines/runtime.js)) and nowhere else**, which is what scopes it: that function is used only by `simTM`, `simLBA` and `simMTM`, so the batch deciders (`testTM3` and friends, each with its own repeat check) carry on deciding — there the repeat *is* the answer, and replacing a correct reject with "no verdict" in a table nobody is watching run would be a loss with nothing bought. **Both the step note and the verdict banner name the setting** when it is off, or a machine the app could have decided reports "no verdict" with nothing on screen to explain why. And **`detectsLoops()` reads absent as on** — a workspace or settings profile written before the setting existed must not load with its verdicts quietly downgraded, the same rule the four `App.config.render` flags follow.

It travels with the workspace through `getWorkspaceData`'s allow-list, beside `twoWayTape`: both change what a run decides, and a file that decides differently when someone else opens it is a file that lies. Settings → Turing.

### Going wide

**Deciding a word is single-threaded; deciding a *list* of them is not.** [js/parallel/](js/parallel/) is a worker pool over the two workloads in the app that are the same shape — N independent runs over one unchanging machine — and nothing else. It is an optimisation, never a capability: every path through it ends in a verdict, and the verdict is the one the serial path would have produced.

```
snapshot.js       App -> a structured-cloneable machine, and back
decide-core.js    one message in, one message out. The part with a test.
decide.worker.js  three lines of plumbing around decide-core
pool.js           sizing, the work queue, and every way back to serial
```

The two callers are `runBatch()` in [js/simulation.js](js/simulation.js) and the Language fingerprint's scroll-driven `pullPrimed()` in [js/language.js](js/language.js). Both keep their serial path and take the pool only when `shouldParallelize()` says the job is big enough to pay for it.

Points worth keeping in mind:

- **The serial and parallel paths are the same function, not two implementations.** [js/machines/batch.js](js/machines/batch.js) splits the batch tester into `decideBatchRows()` (the map, which is what a worker runs on a slice) and `summarizeBatch()` (the fold, which is cheap and always runs on the main thread over the merged rows). `computeBatchResults()` is those two composed. A batch that scored differently depending on how many cores the reader has would be far worse than a slow batch, so there is deliberately no second copy that could drift.
- **Order is carried, never assumed.** Chunks complete in whatever order the scheduler decides, so each carries the offset it started at and is written back into place. Nothing downstream sees completion order.
- **Every failure ends in the serial computation.** No `Worker` constructor (the `node --test` run, and any CSP that refuses one), a worker that throws, a worker that dies mid-job, a chunk answered against a stale machine — each comes back as a hole, and the holes are filled by running those items here. `runParallel` also counts liveness, because if *every* worker dies on load nothing would call `finish()` and the caller would await a promise that never settles.
- **`disabled` is latched, which makes it exactly the state that leaks between tests.** Once a CSP has refused a worker it will refuse the next one, so retrying per batch would cost a throw each time. `resetPool()` exists for `resetModuleState()` in [tests/harness.js](tests/harness.js): without it, the one test exercising the all-workers-died path would send every later test down the serial branch, and they would keep passing while testing nothing.
- **Small work must not get slower.** Spawning eight workers to decide twenty DFA words costs more than deciding them, so `MIN_ITEMS_FOR_POOL` is 32 — but a Turing machine word is a run to `maxTmSteps`, so `EXPENSIVE` machines go wide from four. Workers are then kept warm for a minute, because a second batch or another scroll page usually follows within seconds.
- **The snapshot is not the save format.** `getWorkspaceData()` carries the camera, notes, dividers and the info card, none of which change a verdict, and it lives in a DOM-bound module. `snapshotMachine()` carries exactly what `js/machines/**` reads — the list came from grepping the layer for `App.`, and [tests/parallel.test.js](tests/parallel.test.js) re-derives it, so a simulator that starts reading a new field fails there rather than deciding differently on a worker than on the main thread.
- **The first fingerprint pull stays synchronous.** It is what decides whether the grid is drawn at all (`if (!shown) return`), so making it async would mean appending a fingerprint that might turn out to have no cells in it. Only the scroll pages — where the cells actually accumulate, up to the cell cap — are primed through the pool.
- **`build.worker.format` is `'es'` in [vite.config.js](vite.config.js)**, because the worker is constructed with `{ type: 'module' }`. Vite's default is `iife`, which happens to parse as a module while the bundle stays self-contained — a coincidence rather than a guarantee, and one that stops holding the moment the worker needs a shared chunk.

### The tape

**Where the head may go is a property of the tape, not of the machine driving it**, and [js/tape.js](js/tape.js) is the object that holds it. Determinism, tape count and end markers were already independent axes; boundedness-at-the-left was a fourth with nowhere to live, so it was written out as `if (head < 0) head = 0` in `testTM3`, `testMTM3` and `simTM`, again as `Math.max(0, …)` in the two nondeterministic explorers, and a sixth time inside `normalizeTapeConfig`.

That clamp is not a tape model. A bounded tape should refuse to move left; re-reading cell 0 forever is neither halting nor moving, and since the loop detector then calls the configuration repeated, a machine that scans off the front of its input is **decided wrongly rather than refused** — reported as a clean rejection, indistinguishable from a real one. Every Turing machine imported from a `.jff` hit exactly that, JFLAP's tape being two-way.

One implementation serves all three models: cells live in a `Map` keyed by integer, which has no least index; a bounded tape is that `Map` plus a floor at 0; and an **LBA's is that plus a ceiling (`rightBound`) and two cells that refuse to be written (`immutable`)** — which is the whole of what makes it linear-bounded, stated once in `makeLbaTape` rather than reassembled in `testLBA3` and `simLBA`. `tape.js` imports nothing and takes `blank` as an argument, so a tape is testable without a machine, an `App` or a DOM.

**`move()` and `write()` report a refusal rather than acting on one**, because the callers disagree about what it means: a bounded TM shrugs and re-reads the cell, an LBA rejects. Baking either answer into the tape would just move the old duplication somewhere new.

Points worth keeping in mind:

- **`usesTwoWayTape` in [js/state.js](js/state.js) answers from two places, and the order matters.** `ITM` says so by *being* what it is — no setting may make a machine labelled "Two-Way Infinite TM" bounded — while `TM`, `NDTM` and `MTM` read `App.config.twoWayTape`. That setting is what makes a two-way multi-tape or nondeterministic machine a *tape choice* rather than two more rows in the machine picker. `LBA` is excluded outright: bounded at both ends is its definition, not its tape's.
- **`key()` is origin-independent, and that is the whole of loop detection.** A two-way tape renumbers every cell the moment it grows leftward, so a key built from absolute indices calls two identical configurations different and the frontier never closes. It is built from `snapshot()`, whose window starts at the leftmost of the head and the written cells — pointedly *not* at cell 0, which would anchor it to an origin the machine cannot see. Trailing blanks are trimmed for the same reason: a head that ran right over blank tape and came back is in the configuration it started from.
- **A blank write deletes the cell** rather than storing a blank, or a tape scrubbed back to empty keeps every cell it ever touched and no two such configurations compare equal. The trailing-blank trim in `key()` is therefore **off for a right-bounded tape**: there a trailing blank is a cell the machine wrote, not tape the head has not reached, and trimming would call two different configurations the same.
- **The storage abstraction stops at the tape.** The PDA family was already factored this way — `applyPdaStoreTransition`/`pdaPeek`/`pdaStoreToString` take a `queueMode` flag, so DPDA/NPDA/QA/Counter/2PDA share one store. The two-way *heads* (`2DFA`, `2NFA`, `2DFT`) deliberately stay separate: they never write, and running off an end is a halt condition rather than a move to refuse, so `Tape` would be the wrong shape for them.
- **The drawn head index is not the cell number.** `snapshot()` returns both; on a two-way tape they diverge as soon as it grows left, which is why `simTM` puts the cell in its note — and why `view()` carries the `origin` and the tracker labels each cell `origin + i`.
- `testITM3` and `simITM` are now one-line delegations to the `TM` pair — the difference lives in the tape, and a second copy of the loop is only a way for the two to drift.

`App.config.twoWayTape` defaults to **false**, so an existing machine keeps deciding what it decided; the setting is in Settings → Turing, and travels with a workspace through `getWorkspaceData`'s allow-list. [tests/tape.test.js](tests/tape.test.js) pins the tape itself, the axis, and that one machine decides differently under the two models.

### How many tapes

**MTM is the one machine whose arity is a setting, and the whole of what went wrong there was that number living in two places.** `App.tapeCount` is the machine's; `#tape-count-sel` in the right panel was the control's, and nothing ever filled it in — so a 3-tape file opened showing "2", a wrong number over a δ the panel beside it draws in Γ³. It was a trap as well as a lie: `setTapeCount` compares against `App.tapeCount`, so the reader who picked the number already on screen did not get a no-op. `syncTapeCountUI()` in [js/view.js](js/view.js) is subscribed to `Change.GRAPH` and called from `applyMachineSwitch`, because revealing the control is not the same as filling it in.

- **Changing the arity reshapes the transitions; it does not delete them.** It used to clear `App.transitions` outright, which made the control useless for the one thing anybody wants it for — adding a work tape to a machine that already runs. Nothing about a k-tape rule stops being true when a (k+1)th tape appears, so `setTapeArity` in [js/machines/index.js](js/machines/index.js) pads with a blank read, a blank write and a stationary head, and the machine goes on deciding exactly what it decided. It is one rule rather than two because the wizard's `setDraftTapeCount` reshapes the same three fields on draft rows.
- **Widening is applied outright and narrowing asks**, since only narrowing costs the reader work. The question names the tapes being dropped, and says so when the drop merges two rules into one read tuple — δ is single-valued here, and `tapeArityCollisions` reports only a clash the narrowing *creates*, never one the machine already had.
- **Every path that does not take the new number puts the picker back**, including the one where the reader picks the arity the machine already has. The select has already moved by the time `onchange` fires; the restore happens *before* the confirm is shown, the way `setMachine` restores the model picker, so a refusal leaves a control that already agrees with the machine and the shared confirm dialog keeps its one registration.
- **The k-head step is one function.** `applyMultiTapeStep` in [js/machines/turing.js](js/machines/turing.js) is what `simMTM` and `testMTM3` both call. Written twice, they disagreed: a wildcard write means "put back what you read" everywhere in the app, and both multi-tape loops wrote the wildcard *symbol* onto the tape instead — a rule the reader can build in the dialog, leaving a Σ in a cell that is in no alphabet.
- **`parseMultiTapeInput` returns two shapes and both simulators read both.** The unwrapping used to sit in the definition's `simulate` line and nowhere else, so `decide` got the raw `{tapes: […]}` and passed it to `makeTapes` as a token list — every multi-tape row in the batch tester threw, and with it every StateMate verification of a multi-tape candidate. `multiTapeSeed` is now the single way in. **`simMTM` takes exactly one parameter** for a related reason: `simulateMachine` calls `simulate(input, m)`, so a second positional here silently receives the machine *name*.
- **A tape machine's Read menu offers Γ, not Σ.** `populateTransitionModal` built it from Σ ∪ {⊔}, so every work symbol the machine writes was one you could write and then had no way to select as a read — and on a multi-tape machine that is essentially the whole content of tapes 2..k. Σ stays in the list because the input is written on the tape.

- **How many tapes is a setting, and the arity itself is not capped.** `MIN_TAPES`, `TAPE_LIMIT` and `maxTapes()` in [js/state.js](js/state.js) are the one declaration; `App.config.maxTapeCount` (Settings → Turing, default 8) is what the reader raises, and the picker's options and the wizard's are both generated from it. Four was written down in seven places — the picker's markup and clamp, the wizard's clamp, validation and option list, StateMate's schema and its agent tool — and it is not a fact about anything: k tapes are k `Tape` objects and k columns on a transition, and nothing in the simulators, the tracker or the save format counts to four. `TAPE_LIMIT` is a limit on the *dialog*, not on the machine layer.
- **`maxTapes()` is never smaller than the machine on the canvas.** The setting bounds what you can pick, never what you can open: a file declaring twelve tapes is a twelve-tape machine whatever this reader's preference says, and a picker that could not show its own machine's arity would be the two-places-for-one-number bug again. `clampTapeCount` is what `loadData` applies, so the only thing a file cannot ask for is an arity the app cannot draw.

[tests/multitape.test.js](tests/multitape.test.js) pins the arity as one number, the reshape in both directions, the k-head step, that a four-tape run draws four rows and a seven-tape one seven, and that the offered range follows the setting.

### What a step remembers

**The tracker only ever draws one step, so nothing needs a stored tape per step** — and that observation is worth about three orders of magnitude. A tape machine's step used to carry the whole tape window *twice*: `step.tape` from `snapshot()`, and `step.view.cells` from `view()`, which calls `snapshot()` again. That is `O(steps × window)`, and the window is how far the head has travelled, so a machine that walks off down its tape costs the square of its run.

Measured at the default `maxTmSteps` of 10,000: **921 MB**, on default settings. Loop detection does not save you — a head crossing fresh blank tape never repeats a configuration, so the run goes the full budget and reports `timeout`. A machine whose head stays in a small region cost 11 MB, which is why this went unnoticed: the pathological case is exactly the runaway machine a teaching tool gets pointed at on purpose.

[js/tape-log.js](js/tape-log.js) keeps the initial cells, and per step the head position and the single cell that step wrote — three parallel arrays rather than an object each, since a run is tens of thousands of them and an object header apiece is most of what they weigh. `tapeStep()` builds a step whose `tape`, `head` and `view` are **getters on a shared prototype**, so no call site changed: the tracker, the minimap, StateMate's prompt and the UTM visualiser all still read `step.tape`. The same run now measures **2.4 MB**, and the per-step cost is flat (248 bytes) rather than growing with travel.

- **There are no checkpoints, deliberately.** Replay is one `Map.set` per step, so rebuilding step 10,000 from scratch is well under a millisecond — and the one-entry cursor means playing *forward*, the overwhelmingly common case, applies a single write per step and replays nothing. Checkpoints would have bought a bounded backward scrub at the cost of a periodic full `Map` clone, which is most of the memory this exists to avoid.
- **`noteWrite` records what the cell holds afterwards, not the symbol asked for.** A write an LBA's end marker refused and a blank write (which *deletes* the cell rather than storing a blank) then both replay as exactly what happened, rather than as what was intended.
- **`view.cells` is the step's own `tape` array, not a second copy**, which was the other half of the old cost. Nothing mutates either; every reader that needs to copies first.
- **It is the four deterministic tape machines only** — `TM`, `ITM`, `LBA`, `MTM`, which are precisely the ones that hit the quadratic. `simNDTM` keeps full snapshots because it cannot use this: its consecutive steps are different *branches* off a queue rather than successive configurations of one tape, so there is no delta between them.
- **The window rule is duplicated from `Tape.snapshot()` and must not drift**, so [tests/tape-log.test.js](tests/tape-log.test.js) checks the rebuild against `snapshot()` itself across the bounded, two-way and right-bounded cases rather than against its own expectations. It also pins that read order does not matter (forward, backward and scattered access agree), and — the guard against the whole thing coming back — that `tape`, `head` and `view` are **not own properties** of a step.
- The spread is gone from the window rule (`Math.min(head, ...keys)`): on a tape this module exists to make large, that is an argument list with an engine limit on it.

### What a step remembers, when it is not a tape

**The same fact was true of every machine that is not a tape machine, and it was the largest single cost in the app.** [js/machines/step-log.js](js/machines/step-log.js) is the companion to `tape-log.js`, and the shape of the bug was identical: a step held a copy of an array that grows with the run, so a run was quadratic in the word.

It ran in two directions at once. `remaining` was `tokens.slice(i)` — a fresh suffix copy per step, so a word of length *n* allocated *n* arrays totalling *n²/2* cells. `outToks` was `[...outputs]` — the same quadratic seen from the other end, a fresh copy of a *growing* array. Measured on a DFA: **23 MB at 1,000 symbols, 122 MB at 4,000, 1,036 MB at 16,000**, and a 100,000-symbol word exhausted a 4 GB heap. The step budget does not bound it, because a streamed run retains its steps as it goes — streaming defers the allocation rather than removing it.

Neither is information the step owns. `remaining` is a suffix of the one shared token array, so a **position** describes it completely; `outToks` is a prefix of one growing output, so a **cons list pointer** does. Both are getters on a shared prototype, exactly as `tapeStep` does it, so no reader changed. Step storage is now **186 bytes/step and flat** — the same order as the tape machines' 137 — and a 64,000-symbol word costs 11 MB.

Points worth keeping in mind:

- **Three prototypes, not one, and the split is load-bearing.** A getter always answers, so a single prototype would give every step an `outToks` of `[]` — and `simulation.js` decides whether to draw the Output row on `step.outToks !== undefined`, while `tokIdx` falls back to the playback cursor when a step has no `remaining`. A machine gets the shape it actually has: `wordStep` for the ones that read a word, `outStep` for the ones that emit, `wordOutStep` for the PDT, which does both.
- **The output is a cons list because a search branches.** Moore and Mealy walk, so a shared array plus a length would serve them — but `exploreFST`, `explorePDT` and `explore2DFT` fork, and two branches that agree on their first *k* outputs should hold one prefix rather than two copies of it. `outPush` is O(1) and allocates one node; `outArray` rebuilds on read, which is bounded because only one step is read at a time.
- **The prototypes are composed with descriptors, never `Object.assign`.** Assigning from a prototype *invokes* the getter and copies its value, which is the one mistake that would put the copies straight back.
- **The PDA's configuration lost its suffix too, and its key got cheaper for it.** `pdaConfigKey` took the unread input and joined it; it takes the position now, which identifies the same thing exactly — the token array does not change during a run — and costs a number instead of a join per configuration the search touches. `cfg.stack` is still a real per-branch array, but `buildPdaPathSteps` **shares** it rather than copying: `applyPdaStoreTransition` returns a fresh array per configuration and nothing mutates one afterwards.
- **Three constant arrays were copied per ω-step** — `tokens`, `tape` and `view.cells`, all three fixed for the whole run — and the two-way heads copied their display tape twice per step. Those are shared now, which is the rule `tape-log.js` already states for `view.cells`.
- **A long word is announced, not refused.** `INPUT_LENGTH_NOTICE` in [js/state.js](js/state.js) is the threshold past which `runSim` prints a line, because what is *still* linear in the word is the drawn input row — the tape tracker builds one cell per symbol. The run is cheap at any length; the paint is not, and the reader is told which they are about to get.

[tests/step-log.test.js](tests/step-log.test.js) pins the invariant the whole thing rests on — **`remaining` and `outToks` are not own properties of a step** — plus that every value is the one the copying version produced, that a branching output shares its prefix, that the three shapes give a machine only the fields it has, and that a run holds one token array however long it is.

### Drawing a tape

**`Tape.view()` is the other half of the model, and [js/tape-view.js](js/tape-view.js) draws it.** `snapshot()` says what the cells hold; `view()` says whether the head could keep going — the bounds as *absolute cell numbers*, `null` for "no wall on this side", plus the marker symbols and whether anything may be written. It comes from the tape for the same reason the clamp does: a machine-name branch in the renderer would be a second, drifting copy of `tape.js`.

Without it the tracker drew a flat row of boxes, which made the four tapes in the app indistinguishable on screen — TM bounded at cell 0, ITM infinite both ways, LBA bounded at both ends with two unwritable cells, 2DFA read-only between markers. Every one of those differences is a fact about an *end*, and an end is exactly the part a row of cells cannot show: a wall and blank tape running on forever look identical cell for cell. So a row is cells **between two caps** — a hatched wall where the tape stops, a fade into `⋯` where it does not — and the caps are the content.

Points worth keeping in mind:

- **A simulator attaches the descriptor; it does not describe itself.** `step.view` (`step.views` for MTM) is written straight from `tape.view()`. The two-way heads have no `Tape` at all — see [the tape](#the-tape) — so `twoWayTapeView` in [js/machines/twoway.js](js/machines/twoway.js) builds the same shape by hand, and `simOmega` builds one carrying `periodFrom`/`periodLen`, because what continues past an ω-word's right edge is the repeating block rather than blank tape. **A step with no `view` still draws**: it falls back to a bounded strip and declines to claim anything about the ends, rather than guessing at them from the machine's name.
- **`js/tape-view.js` imports nothing and reads no `App`.** A row is drawn from the descriptor it is handed, which is what lets `tape.js` hand one over, the two-way heads build one, and the UTM visualiser in `algorithms-fa.js` reuse the whole thing rather than keeping a second tape drawn in inline styles.
- **Cells are reused across steps, keyed by absolute cell number** — the same rule `renderAll()` follows for states. The old tracker rebuilt its `innerHTML` every step, so the CSS transition on a cell never once fired: the highlighted node was always a brand new element with no previous state to animate from. Keyed by *position* instead, a two-way tape growing leftward would reuse every cell as its own neighbour and the row would appear to shift by one.
- **`followHead` scrolls only when the head has actually left the band**, and its clearance is capped at a quarter of the strip — these panels are resized down to widths where three cells is the whole visible band, and an uncapped pad re-centres on every step. It reads `offsetLeft`, so **`.tv-track` must stay `position: relative`**: without it the measurement is taken against the right panel and the strip scrolls to a coordinate in the wrong box.
- **What is not a tape is not drawn as one.** A stack, a queue, an output and a probability distribution are *track* rows: the same cells, no caps and no cell numbers, because a stack's ends are a top and a bottom rather than a wall and an infinity, and its positions are depths wearing the same numerals. `capL`/`capR` name them instead.
- **The input row of a finite automaton passes every test for a bounded read-only tape, and saying so would be true and useless.** A view may carry its own `say` to override the derived phrase; the input row's reports `|w|`.

[tests/tape-view.test.js](tests/tape-view.test.js) pins that the four tapes still read differently — the caps, the markers, the negative cell numbers, the node identity across steps — and `tests/tape.test.js` pins that the bounds `view()` reports are the ones the tape actually enforces, since a drawn wall the head can walk through would be worse than no wall.

### Space-time diagrams

**The tracker draws one configuration; [js/spacetime.js](js/spacetime.js) draws all of them** — time down, space across, one row per step, the head's path threaded through the rows. It is a right-panel section (`rp-spacetime`) like any other, collapsed by default and hidden on machines without a tape, and the tracker header's grid button opens it straight into a floating window, because a diagram of a whole run wants more width than a sidebar has. [js/spacetime-ui.js](js/spacetime-ui.js) is the part with a page attached.

- **The tape log is the source, and it is read in place.** Asking each step for `step.tape` would rebuild a window per row — the O(steps × window) [js/tape-log.js](js/tape-log.js) exists to avoid, paid again on read. `journal()` hands over the log's arrays by reference and the model replays them itself, one write per row, with a `Map` checkpoint every 256 rows so a viewport halfway down a long run is a short replay. Steps that store their tape (the two-way heads, whose tape never changes) are read directly. `stepJournals()` is the one place that knows a logged step's representation.
- **It never pulls.** `model.extend(reachableCount())` indexes the steps that exist and stops — the scrubber's own count, so a block run's diagram ends where the block did and a streaming run's grows as it plays. Growing the rest is `computeRestOfRun()`: the ⏭ drain, same slices and same timer, with the playhead left where the reader put it.
- **Columns are absolute cell numbers, fixed for the whole diagram.** A two-way tape renumbers its tracker window when it grows left; a diagram that did the same would shear sideways at every such step. The UI scrolls by the growth instead, so the picture holds still under the reader.
- **One painter for every output.** `paintSpaceTime` draws against a 2D-context-shaped surface: the window's canvas, the PNG's canvas, and `svgContext()`, which records inline-attributed SVG elements instead of pixels. Two renderers would be two pictures that drift, and an export is only worth having if it is the one on screen. The SVG carries no stylesheet, class or CSS variable, so it renders the same in Inkscape and inside a LaTeX figure — `tests/spacetime.test.js` asserts that.
- **The canvas is the viewport, never the diagram.** Ten thousand rows at 8px is past every browser's canvas limit; a spacer gives the scroller the diagram's size and the canvas repaints the visible window, gutter and ruler pinned. A paint costs what is on screen, and nothing at all while the section is collapsed.
- **Symbols are identities, so the palette is categorical and fixed to Γ's order** (Σ first, so the input gets the most separable slots) — a symbol is the same colour on every run. A space-time grid puts every pair of symbols side by side, and only three categorical hues stay apart under every colour-vision deficiency, so colour is never asked to work alone: from 13px the symbol is printed in its cell, the hover readout names it at any size, and the legend is always shown. A ninth symbol folds into a neutral grey rather than getting a generated hue.
- **Below 13px the head's path is drawn over the cells with a halo; above it the path goes under them** and each glyph is cut out of it with a ring of the ground. Drawn over printed symbols it read as a strikethrough. Head rings are drawn only at glyph size — a ring on every row as well as the path read as a chain of boxes — and the current step's head gets an accent ring at every size. Fills are softened above 3px for the same reason: a long run of one symbol at full saturation is a slab that drowns the path.
- **Following the playhead glides (200ms, ease-out) rather than jumps**, and is judged against where a glide in flight is *going*, or fast playback would restart it from mid-air every tick. It is skipped under reduced motion and for a jump of several screens, and any wheel or press on the diagram cancels it. Measured on a 10,000-step run: scroll, hover and 5× playback hold frame rate with no long tasks.
- **NDTM gets the section and an explanation, not a diagram.** Its consecutive steps are different branches off a queue rather than successive configurations of one tape, so a diagram would interleave unrelated branches and look like a machine that teleports. `spaceTimeKind()` answers `tree` for it.
- **The overview strip is the whole run in the window's height** — symbol colour averaged into bins, the head's path, a box for what the diagram shows, the playhead, and bars on its edge for a loop's span, a block boundary and the verdict. Click goes there, dragging the box pans, double-click moves the playhead, the wheel scrolls the diagram. It appears once the diagram is more than two screens tall (and goes below one and a half, so it cannot flicker at the line) and the toolbar can turn it off. Its left edge is a handle (`.st-ov-grip`): the dragged width is a per-browser preference in `localStorage`, never the workspace, and `stripWidth()` clamps it to half the view on every paint, so a width chosen in a wide window cannot swallow the diagram once the section is docked. Double-click or Enter goes back to the automatic width.
- **It counts durations, not cells.** `makeOverview` credits each non-blank cell's stretch of rows to its bin when a write ends it or a bin boundary cuts it — work per row, per write and per live cell per bin, never rows × cells. Bins are power-of-two sized and *merge* as a streaming run outgrows them, in time and in cells, so the strip rescales only when the run doubles and a two-way tape growing left merges rather than rebuilds. Merging is exact because counts add and cell bins are aligned from cell 0; the tests check every grid against a brute-force count through repeated merges.
- **The strip is drawn per device pixel, never stretched.** It began as one pixel per bin scaled up with smoothing on, so an eighteen-cell tape was eighteen pixels blurred across fifty. Now the bins are sized to the strip (`stripBins`: never more than it has device pixels, either way), `renderOverviewBase` gives each device pixel the bin under its centre into a cached canvas at device resolution, and each frame copies that 1:1 with the moving parts drawn over it. The main diagram's scroll offsets are snapped to device pixels for the same reason. The whole-run export scales by whole pixels with smoothing off, which was already sharp.
- **"Whole run" export is the same object built once, `fixed`**, with bins sized so the plot is at most 1600px tall: the one way a ten-thousand-step run fits in a file. The dialog opens on it when the cell-by-cell picture would be refused. The SVG embeds the cells as one pixelated image and draws everything else as shapes.
- **Export is a dialog of its own, not an `ExportFormats` entry**: that registry builds from the machine's IR and this is a picture of a run. PNG, SVG, aligned text (`[x]` marks the head — the form that pastes into a paper) and CSV (one line per step and tape, over one shared set of cell columns). A size too large for one image or one usable SVG is refused with the way out named — a range of steps, or a smaller cell.

- **A pushdown machine gets a diagram too, and it is the same diagram.** `spaceTimeKind()` answers `store` for every single-array store (`isAnyPDA`: stack, queue, counter, two stacks, PDT), and the UI hands the model its rows as `tracks` — the input, each store, and the PDT's output — read off each step with `viewOf`. A stack is drawn bottom-left with a wall there and its top as the head, so **the head's path is the stack's height over time**; a queue is drawn front-left and read at its front. The EPDA is left out on purpose: a stack of stacks is not a row of cells. The overview follows a store by *diffing* each row against the last, since a stack has no journal — the same event a tape's journal records, found by comparing.
- **The NDTM draws the branch that accepted.** Its search yields configurations in the order it dequeues them, so the steps are unrelated branches — but each now carries `parent` (the branch it was expanded from) and `via` (the transition), and `acceptingBranch()` walks back from the accept to the root. That branch is one timeline and is drawn like any run; `stepOfRow`/`rowOfStep` map between its rows and the search's steps, so scrubbing either moves the other, and the footer says so when the player is standing on a branch the diagram does not draw. A search still running, or one that ended without accepting, gets a sentence instead of a diagram.
- **Alt-click a cell: who wrote this?** `model.lastWrite(t, row, x)` finds the write that put the cell's symbol there — a journal entry for a tape (a write of the same symbol still counts: it *was* written), a change for a stored row. The diagram marks every row that wrote the cell and the stretch since the last write; the bar under it names the step and the transition (`transLabel`), goes there, and walks back one write at a time. Read-only rows say they are never written.

### The complexity profile

[js/complexity.js](js/complexity.js) runs the machine on inputs of length `from`..`to` and measures each run: steps taken, and space — cells the heads visited for a tape, the tallest the store got for a pushdown machine. [js/complexity-ui.js](js/complexity-ui.js) is the `rp-complexity` section: two small charts (steps against n, space against n — two charts, never one with two y-axes), worst case solid and mean dashed, a growth reading on each, a table, CSV.

- **Two ways to choose inputs, because they answer different questions.** *Every word* is worst case over Σⁿ, sampled past a cap — always the one-symbol words, the rest from a seeded draw so the same profile twice is the same profile. *Family* is one structured word per n from a pattern like `a^n b^n`, `(ab)^{2n}`, `1^n+1^{n+1}`; most machines only work hard on inputs of a shape. `parseFamily` fails with a sentence the reader can act on.
- **Measuring never touches the run on screen.** `traceMachine()` in [js/machines/index.js](js/machines/index.js) runs from the machine's own start (the player's block subject lifted, as `decideMachine` lifts it), paints nothing, and puts `App.simSteps`/`simIdx`/`simRun` back — a search-based simulator writes `App.simSteps` as it goes.
- **The profile is a generator, run in slices** of about a frame, so the charts grow as lengths finish and Stop, the canvas and the rest of the app stay live. A run that hits its step budget is drawn hollow and left out of the growth reading: its value is only a lower bound.
- **The growth reading checks finite differences before it fits a slope.** A log–log slope is thrown by constants (n + 1 over n = 1..7 reads as n^0.83), while the first differences of any line are constant and the second of any parabola — and step counts are very often exactly such polynomials. Exponential needs steady ratios that do not drift toward 1, which is what tells it from a polynomial over a short tail. It says it is an estimate, not a proof.
- **A point is a word.** Hovering names the worst word at that length; clicking runs it in the player and opens its space-time diagram. On the example binary adder, `1^n+1^n` reads ≈ 2.26ⁿ — it adds one unit per lap, and 1ⁿ in binary is 2ⁿ−1 — which is exactly the kind of thing the profile exists to show.
- The section is built the first time it is shown, not on every graph edit; an edit after a profile marks it stale rather than discarding it.

[tests/complexity.test.js](tests/complexity.test.js) pins the pattern language and its errors, the sampling, that a measured run is the run the player would show, the growth readings on curves whose answer is known, a quadratic machine reading as quadratic, and that the player is untouched.

[tests/spacetime.test.js](tests/spacetime.test.js) pins the invariant the rest rests on — **row *i* is the tape the tracker shows at step *i***, cell for cell at absolute positions, across TM, ITM, LBA, MTM and 2DFA — plus random access across checkpoints, that building a diagram pulls nothing from a streaming run, that colours follow Γ rather than discovery order, and that the SVG stands alone.
