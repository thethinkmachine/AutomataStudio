### Very large machines

**Past a few hundred states the diff stops being the answer, because the cost is in the nodes existing.** A 1000-state machine is ~15,000 SVG elements; an unchanged render allocates nothing and the browser still re-rasterises every one of them on every pan frame, every zoom tick and every theme repaint. Four things follow, and the through-line is that **the model stays whole and only the DOM becomes a view of it** — every state is still simulated, measured, exported and decided.

- **[js/viewport.js](js/viewport.js) decides what exists.** `cullViewport()` is called once at the top of a render, so states and edges cannot disagree about where the screen is; a node that scrolls out is *evicted*, not hidden, because `display: none` still costs a box. The margin is a full screen each way, so ordinary panning reuses nodes rather than thrashing them, and `cullNeedsRepaint()` is what makes a pan cost a transform and nothing else until it has travelled that far. `renderTransitions` tests the geometry rather than the rect — `buildLayoutContext` lays out only the edges near the screen, so a missing `geo` *is* the cull result, and testing it before the node is built is what stops an off-screen edge being created and torn down every frame.
- **Level of detail is separate from culling and applies at any size.** Below `LOD_LABEL_ZOOM` a label is a two-pixel smear costing a text node, a shaping pass and a raster; it takes the same branch as the "labels off" setting, whose whole point is that a hidden label is never built. The LOD cache key is a value of its own (`'::lod::'`) rather than an empty name, or coming back from a zoomed-out view would match a stale key and leave the names off.
- **`withFullRender()` is the exception, and there is exactly one kind of caller.** Anything that *looks* at the canvas is fine with a window; anything that reads it **back** is not. `buildExportSVG` clones the live SVG while its crop box comes from the layout pass, so a cropped export taken mid-pan would be a viewBox around the whole machine containing the part that was on screen. The repaint on the way out is not optional either.
- **Both flags are in Settings → Canvas and follow the `render.*` rule that absent means on** (`cullOffscreen`, `zoomLOD`), so a workspace written before they existed does not load with them off.

**The three id lookups are indexed, and the indexes validate themselves rather than being invalidated.** `getState` was 112 call sites of `App.states.find`, several inside per-transition or per-frame loops; `getTransition` the same, which made `syncSelectionClasses` after a select-all four million comparisons plus two thousand document-wide selector matches. Nothing in the app announces that `App.states` changed — it is pushed to, filtered and reassigned from twenty places — so `stateIndex()` in [js/state.js](js/state.js) checks array identity, length and the two end elements, which catches every mutation the app performs. `groupTransitions` in `geometry.js` caches the per-pair grouping behind the same test plus the index's identity, because grouping depends on neither list's coordinates and the pass runs sixty times a second during a drag.

**Three loops were quadratic in the machine and are not any more.**

- `resolveNodeOverlaps` ran 24 passes of n²/2, so dropping one state on a 1000-state machine cost twelve million distance tests before the pointer came back. Past `OVERLAP_GRID_STATES` it sweeps a uniform grid instead. The cell each state was *filed under* is kept rather than recomputed — the pass moves states as it goes, and asking a state which cell it is in now sends the query looking in a neighbourhood the grid never filed its partners into.
- The trace log was rebuilt from step 0 on every tick, so a Turing machine got slower with every step it took: at `maxTmSteps` one tick meant building and parsing ten thousand divs, ten thousand times over. Only `SIM_LOG_TAIL` steps are written; the log scrolls itself to the bottom, so everything above the last screenful was being built to be scrolled past, and the scrubber is what navigates a long run.
- `updateSimCanvasHighlights` recomputed the whole trail on every step, resolving each step's transition by scanning `App.transitions`. It is carried forward now (`App._simTrail`, keyed on the steps array); only a scrub *backwards* rebuilds, bounded by where it lands. Playing back 4000 steps of a 1000-state machine went from ~59s to ~1.7s.

**`App.history` is bounded by bytes as well as by depth.** An entry is the whole workspace as JSON; 300 of them on a thousand-state machine is a hundred megabytes of retained string for a session that has done nothing but drag states around. The depth limit stays because on a small machine it is the friendlier one and is never the one that bites.

**Those two limits bound the *live* stack, and a third bounds the others.** Every background tab holds a full stack of its own — `exportWorkspaceState` copies `history` and `future` into the tab's blob and `Workspaces` keeps every blob alive — which measured at **3,579 KB of stack against a 62 KB machine, 98% of the tab**, and 105 MB across eight of them. `trimStowedHistory` in [js/history.js](js/history.js) caps a tab on its way into the background (`HISTORY_STOWED_MAX_ENTRIES`, `HISTORY_STOWED_MAX_BYTES`), keeping the **newest** entries because both stacks are popped from the end. `stripTabForStorage()` already made this call for persistence, naming the stacks as the single largest cause of quota failure; this is the same reasoning applied to memory. What it costs is depth: a tab you are not looking at remembers its last forty edits rather than all three hundred.

**The trim lives in `stowActiveWorkspace()` and deliberately not in `exportWorkspaceState()`.** That function has three other kinds of caller — StateMate's stash-and-restore above all, which imports a candidate to verify it and restores in a `finally` — and every one of them must round-trip a workspace *exactly*. Trimming there would quietly cost the reader undo entries on every verification.

**And a history entry is copied as an array, never entry by entry.** `exportWorkspaceState` used to map `JSON.parse(JSON.stringify(h))` over the stack, which re-escaped each entry into a new string and parsed it back out — twice the stack's size in transient garbage per tab switch and per autosave, to arrive at a value equal to the one it started with. The entries are already JSON strings (`serializeState()` returns `JSON.stringify(…)`, and `historyBytes()` sums `entry.length`) and strings are immutable, so there is nothing for a deep copy to defend. [tests/history-memory.test.js](tests/history-memory.test.js) pins the trim, the byte budget, that one entry always survives, and that `exportWorkspaceState` still round-trips the whole stack.

Two more, in the same spirit: `formatSet` prints a set past `SET_PRINT_CAP` as its ends and its size — KaTeX typesets a thousand-element Q into a thousand boxes on every structural edit, and nobody reads the four hundredth member. And `deriveRegex` refuses past `REGEX_DERIVE_MAX_STATES`: state elimination is cubic in |Q| and allocates a |Q|² table before it starts, so a 400-state DFA is not a slow computation but a locked tab. The panel says the class is asserted rather than derived, which `App._regexIsDerived` already distinguishes.

**How far out the camera may go is a property of the diagram, not a constant.** `App.config.zoom.min` was a flat 20% — generous for a ten-state machine and a wall for a thousand-state one, whose whole-machine view wants 7%. Clamped up, *fit-to-screen itself stopped fitting*: it framed a box a third wider than the viewport and reported success, so panning by hand was the only way around a big machine. `minZoom()` in [js/canvas.js](js/canvas.js) answers the configured floor **or** the zoom that frames the whole drawing with headroom, whichever is lower, and `clampZoom()` is what every zoom path now calls — the wheel, the pinch, the ± buttons, the zoom field, fit-to-screen, and the minimap's wheel and keys. Two things it deliberately does not do: it reads the **state circles rather than `getContentBounds`**, because a floor does not need to know where a pushed-out label landed and that call runs the whole layout pass, which a wheel gesture must not; and it is **memoised for 400ms**, because nothing announces that a state moved and a gesture asks sixty times a second — a short life is what keeps a state dragged out to the edge from leaving a stale wall behind it.

**A run drawn at 8% has to still be a line.** A stroke width is in world units, so the camera divides it: the trail marking the path a computation took was 1.5px of `--accent` at 35% opacity, which at the zoom a large machine is read at is a fifth of a pixel losing to the theme's own background — on exactly the machines where the route is the only thing left worth reading. Every simulation stroke now carries `vector-effect: non-scaling-stroke`, so its width is in screen pixels and the trail is the same line at 8% that it is at 100%.

**It does not get *thicker* there, and the reason is the arrowheads.** The heads are drawn in world units (`markerUnits="userSpaceOnUse"` in the `<defs>`), so a heavier stroke no longer inflates them the way it did while they were sized against it — but they are still world units, which the camera divides even though it no longer divides the line. Widening the trail would leave a fatter and fatter line running into a head shrinking away from it, coming apart exactly where the two meet. So what changes past the label LOD is the marker and the opacity, not the weight: `applyCamera()` sets **`.zoom-far`** on `#canvas-wrap` below `LOD_LABEL_ZOOM` — the same threshold the labels drop out at, so "the names went" and "the trail came forward" are one place on the zoom dial — and under it the heads come off the trail and the active edge, and the trail stops being quiet, since at four pixels a state there is nothing left on screen for it to be quiet against. The travelling token is sized in JS rather than CSS for the same reason `r` is a world unit: `max(5, 5 / cam.z)`.

**The background grid fades out on the way there**, in [css/views.css](css/views.css), and it is the same arithmetic seen from the other side: the cell scales with the camera while the line stays 1px, so a 40px cell is one part line in forty at 100% and one in three at 8% — the grid stops being a reference and becomes a hatch, moiréing against a diagram whose edges are by then about as thick as it is. Its opacity ramps off between a 24px cell and a 12px one, as a ramp rather than a threshold so it cannot pop in and out on a slow scroll-zoom.

The minimap repaints on **every frame of every pan**, so its draw calls are batched rather than its content skipped: every edge shares one stroke style, so the whole diagram is one path and one `stroke()`; states are bucketed by style, of which there are ever only a handful. A self-loop's arc needs its own `moveTo` or it is joined to the previous edge by a line across the map.

### The large-machine profile

**Everything above degrades by size on its own, and each states its own threshold because each answers its own question.** What was missing was the other half: the costs that scale with the machine and were gated on nothing at all. `largeMachineProfile()` in [js/state.js](js/state.js) is that fact stated once, and five modules read it.

**The line is the collision budget** — `COLLISION_BUDGET_STATES` / `COLLISION_BUDGET_TRANSITIONS`, now declared in `state.js` and re-exported by `geometry.js` where they used to live. It was measured rather than guessed, and "past what a layout pass can afford in a frame" is a good definition of "too big to draw in full", so the profile reuses it instead of introducing a sixth number the others can drift from. `state.js` is import-free and cannot reach `geometry.js`, which is why the constants moved rather than being copied.

What it turns off, and why each one was on the list:

| | cost without it |
| --- | --- |
| edge labels (`edgeLabelsHidden`) | built at any zoom above the LOD threshold, for the whole cull window — nine screens of content, so a machine dense enough to cull paints a wall of pills over its own diagram |
| eased layout (`animEnabled`) | four tracks per edge, so a structural change leaves thousands converging and rAF stays busy until they settle |
| autosave period (`effectiveAutosaveInterval`) | `JSON.stringify` over every workspace into IndexedDB on a fixed timer — megabytes on the main thread every fifteen seconds |
| minimap rate (`LARGE_FRAME_MS`) | a thousand path commands on every frame of every pan |
| undo depth (`historyDepthLimit`) | the byte cap bounds this by *evicting*, so the stack sits permanently at the cap shifting one entry off per edit |

**It is derived, never written.** Nothing in it touches `App.config`, and that is most of the design. The reader's settings are remembered exactly as they were, the tab is not dirtied, the `.json` is not rewritten, and lifting the override restores the machine's own appearance with no state to unwind — which is what makes a single confirm a complete undo. It also means the profile covers *every* path into a large machine: a load, an import, a subset construction that blows up on the canvas, an undo back into one. Writing `edgeLabelStyle = 'none'` at load would have covered only the path that remembered to ask.

**The override is `render.largeMachineAuto`, and absent means on** — the same rule the four render flags follow, so a workspace written before this existed does not load with the profile disabled. Settings → Canvas and the quick-settings popover both offer it and both ask before letting you turn it *off*; turning it back on is free and never asks. `largeMachineOverridePrompt()` is in `state.js` rather than in either surface because `quick-settings.js` must not import `ui.js`, and one declaration is what stops the two describing the same decision differently.

**Two things are not reads, which is why `syncLargeMachineProfile()` exists.** The autosave timer is a live `setInterval`, so a machine that *grows* past the line keeps the period it was armed with; and a flip has to be said out loud, or a reader whose labels vanish between one construction and the next is looking at a bug. It is idempotent, subscribed to `GRAPH` and `CANVAS`, and called explicitly from `applySettings` — which writes the override without emitting.

**Autosave is stretched, never switched off**, because a large machine is the one you would least like to redraw; `0` still means off, and a reader who chose a longer interval keeps theirs. And **stopping short is as much a part of this as anything it does**: state-name wrapping is a handful of tspans behind the cull window, while un-wrapping overflows a long name out of its circle on the diagram already hardest to read — so `wrapStateLabelsOn()` deliberately does not consult the profile. `clickHighlightMode` is per click, not per frame. `langStepBudget` would change *verdicts*, which must never be automatic. The rule the profile is drawn along is that it turns off what costs frames and nothing else.

**With the labels off, hover is how an edge is read** — so the tooltip stopped being supplementary. `transTipRows()` and `edgeTipFor()` in [js/states-transitions.js](js/states-transitions.js) build a *columnar* description; [js/tooltip.js](js/tooltip.js) renders rows split on `
` and cells on `	` as a grid, with `---` for a rule and a lone cell spanning the width. It stays a **string** because `data-tip` is an attribute — a structured payload would mean a second channel and a second tooltip implementation — and the tab is the whole opt-in, so every plain label is untouched. Two rules: **prose stays the accessible name** (`transLabelDescriptive` still fills `aria-label`, because a screen reader should hear a sentence rather than a table read left to right), and **`transTipRows`'s branch order mirrors the prose version's exactly**, since the family predicates overlap and a reordered copy is a copy that disagrees. The heading names the edge's endpoints, which an unlabelled arrow among a thousand others needs to say first. A five-tape transition was `Tape 1: Read '#', Write '#', Move Right | Tape 2: …` wrapped as prose; it is now a four-column table where two rules on one arrow differ visibly.

**The tooltip's box is bounded; its content is not.** That order matters and the reverse was tried first. Capping the content (a transition count and a tape count) was wrong twice: the two caps *multiplied*, so five transitions on a twelve-tape machine was still seventy-one rows; and what they trimmed was simply gone — "+5 more" with no way to reach it is worse than a long tooltip, because the reader can see something is withheld and has nothing to do about it. On a large machine, where the labels are not drawn, those five may be the whole reason the edge was hovered. So the content is whole, `max-height: min(70vh, …)` bounds the box, and what does not fit **scrolls**. `TIP_MAX_ROWS` survives only so a pathological edge cannot build an unbounded grid on hover; it is far past anything a reader meets, and says so when it trims.

**Which means the tooltip has to be reachable, and only then.** `pointer-events: none` is right for a tooltip that fits — it sits over the canvas and must not take the pointer off the diagram it describes. `.tooltip.is-reachable.show` lifts that, and `show()` sets the class from a **measurement** (`scrollHeight` against the client box) rather than from the content's kind, so an ordinary tooltip is never made to block the canvas on the chance it might have overflowed. Gated on `.show` too, or a tooltip fading out would intercept a click nobody can see it intercepting. Four things then have to be forgiven, and each is invisible to break: crossing the gap from anchor to tooltip is a `pointerout` (`HIDE_GRACE`, cancelled by `pointerenter` on the tip), moving *into* the tip is not leaving (`inTip(e.relatedTarget)`), and the two capture-phase dismissers — `pointerdown` and `scroll` — both see events from inside a scrolling tooltip and would each close it at the first attempt to read it.

**The box that scrolls is not the box with the rounded corners**, and it cannot be. A browser paints a scrollbar's gutter without clipping it to its own element's `border-radius`, so a scrolling tooltip came back with two square corners down whichever side the scrollbar was on. `.tooltip` therefore keeps the radius and clips (`overflow: hidden` under `.is-grid`) while an inner `.tooltip-body` carries the `max-height` and the scroll. That split pays for itself twice more: the keycap chip is a sibling of the body rather than a row inside it, so it stays out of the scrolling area where a shortcut does not belong; and the base `.tooltip` gets *no* `overflow` at all, so a long single-line label still spills out of its box rather than being clipped inside it. The body is `display: inline` by default for the same chip — a block there would drop a `data-tip-kbd` onto a line of its own — and `.is-grid` is the one rule that makes it a block scroll container.

**It scrolls vertically only, and the horizontal axis is the interesting half.** The columns are `max-content`, so the body shrink-to-fits to exactly the table's width — and the vertical scrollbar then takes its 7px out of the content box, leaving the table 7px too wide for the space it just sized itself to. That is a horizontal scrollbar on a table that fits, on every tooltip tall enough to scroll at all, which is why `overflow` is `hidden auto` rather than `auto`. Nothing is lost by refusing it: the outer box is capped at the viewport and a transition table is four short columns, so the content is narrower than the window on anything but a phone — where there is no hover to scroll with in the first place.

**Placement is clamped, and measured from a neutral offset.** `place()` picks below then above, and now clamps `top` into the viewport as well — a tall tip previously just ran off the bottom. It also resets `left`/`top` to 0 *before* reading `offsetWidth`: a `position: fixed` box with `left` set and `right: auto` shrink-to-fits against `viewport − left`, so measuring while the previous hover's offset was still on the element squeezed the width, and that squeezed width computed the next offset. A table hovered near the right edge came back permanently narrow, breaking `Write` into `Wri/te`.

**A table is as wide as its columns.** The prose widths (260px, 300px) are a *measure* — a line length chosen so a sentence reads well — and that reasoning does not transfer to columns, so `.is-grid` is bounded only by the window and its columns are `max-content` with `white-space: nowrap` on the cells. A squeezed column breaks its own header mid-word, which is what a table is for. Touch, where there is no hover at all, holds a table up for 4 s instead of 1.2 s.

[tests/large-machine-profile.test.js](tests/large-machine-profile.test.js) pins the threshold, that `App.config` is unchanged either side of the profile, that the override lifts every part at once, and each consumer. [tests/tooltip-grid.test.js](tests/tooltip-grid.test.js) pins that every machine gets a key column and that the two renderings still describe the same transition.

### Geometry and collision avoidance

**Where things go is [js/geometry.js](js/geometry.js); what gets drawn is `render.js`.** `buildLayoutContext()` lays the whole diagram out in one pass and returns `{stateById, tsByPair, groups, geo}`, where `geo` maps each `"from|to"` key to a finished `{d, lx, ly, mx, my, crvVal, …}`. Both `renderTransitions()` and `updateFastDOM()` start from it — via `currentLayoutContext()` in `render.js`, which supplies the label-measuring callback — so routing runs live during a drag rather than snapping into place on release.

It is one pass rather than one call per edge because avoidance is global: a label can only be placed clear of the other labels once they all have positions. The four stages, each reading the last:

1. **index** — states, transitions grouped per ordered pair, and a uniform spatial grid. Every "what is near here?" query goes through the grid; without it routing is O(edges × states) and label placement O(labels²).
2. **self-loops** — twelve candidate directions scored against nearby states, the label box that would ride outside the arc, and the directions incident edges (plus the start arrow) arrive from. Up wins ties. **A loop is no longer always on top**; `t.loopAngle` is the manual override, set by dragging the grip a selected loop now shows, and cleared by "Reset Shape".
3. **routing** — an edge whose chord runs through a third state is bent around it. A quadratic's deviation is *half* its control offset, so the search steps in node-sized increments. `t.curve` (the bend handle) always wins over it, and an edge crossing more than `MAX_ROUTE_BLOCKERS` states gives up rather than swinging 300px sideways.
4. **labels** — offset off their own edge along the normal, on the outside of the bend, then moved only if that box overlaps a state, another label or a foreign edge. Candidates are ordered ideal-first, so an uncrowded diagram costs one collision test per label.

Points worth keeping in mind:

- **The grid is flat, and what it cost was the key rather than the lookup.** A grid query was the single hottest thing in the app — ~31% of the layout pass at 500 states, ahead of every piece of geometry it exists to serve — and almost none of that was searching. It was building a *string* `${ix},${iy}` per cell per query and hashing it (~45%), and allocating a result array per query to spread the buckets into (~20%). Measured over 20k label-sized queries on 500 nodes: string key + fresh array **9.12ms**, the same writing into a reused array **7.26ms**, an integer key into a Map of arrays **3.96ms**, and the flat open-addressed table with a linked list per cell that is there now **2.02ms**. End to end that is **1.7–1.9×** across every size: the layout pass **10.3ms → 5.9ms** at 200 states, **28.7 → 15.3** at 500 and **66.1 → 39.4** at 1000, and a drag frame **4.05 → 2.9ms** at 200 and **6.2 → 3.7** at 500 (Node, `tests/harness.js`). That is more than the 31% alone predicts, because the allocation it removed was also most of the GC, and because the callers stopped walking a freshly built array per query. A callback in place of the result array was tried and is *worse* (4.6ms): the three call sites pass three different closures, so the call inside the loop goes polymorphic.
- **A query result is only valid until the next query on the same grid.** That is the price of not allocating: `gridQuery` fills a buffer the grid owns and leaves the count in `grid.n`, so a caller reads `grid.out[i]` for `i < grid.n` and must be done before it asks that grid again. It holds at every site today — `labelPenalty` asks all three grids in turn and consumes each before the next, and `chooseSelfLoopAngle` holds a node result across twelve `scoreLoopAngle` calls that query nothing — and a nested query on one grid would silently read the inner result's items under the outer one's count.
- **Two of the three grids are filled *during* the pass that queries them** — the edge samples as edges are routed, the labels as they are placed — which is why the cells are an open-addressed table with a head/tail linked list rather than the counting sort that would be faster. A CSR layout has to be built from a complete list in one pass, and one structure that serves all three beats a second implementation for the one grid that is static. Insertion order is preserved *within* a cell, because the geometry sums float penalties over the result and a reordering is visible in the last bits.
- **Label sizes are estimated, not measured.** The box has to exist before the text is in the DOM, and measuring per edge per frame would force a layout flush on every drag frame. `render.js` and `geometry.js` therefore share the pill metrics (`pillPartWidth`, `PILL_ROW_H`) — two copies of that arithmetic would place the label clear of a box that is not the one drawn.
- **Stages 2–4 are skipped past `COLLISION_BUDGET_STATES` / `COLLISION_BUDGET_TRANSITIONS`**, where a pass no longer fits a drag frame; the geometry degrades to the plain drawing rather than getting slow. The four `App.config.render` flags (`smartSelfLoops`, `autoRouteEdges`, `smartLabels`, `avoidNodeOverlap`) switch the stages off independently, and **absent means on** — an imported config predating them must not read as "all off".
- `resolveNodeOverlaps()` separates state circles, and `canvas.js` calls it on drop with `movable` set to the dragged ids so the crowd stays put. Coincident centres have no direction to divide by; it builds the unit vector directly rather than standing in an epsilon distance, which scaled the push by a thousand and fired the state off the canvas.
- `includeLayoutBounds()` feeds `getContentBounds()`, so fit-to-screen and cropped exports frame loops and pushed-out labels instead of cropping them.

[js/canvas.js](js/canvas.js) owns the camera (`App.cam` = `{x, y, z}`), pan/zoom and pointer gestures, with touch on a deliberately separate path from mouse/pen. `App.dragCurve` covers both edge gestures: bending a chord, or swinging a self-loop when `from === to`.

**Everything on the canvas is selected the same way.** Four id sets on `App` — `selectedStates`, `selectedTransitions`, `selectedNotes`, `selectedDividers` — and one `clearSelection()` that empties all four, because a kind that clears separately is a kind that survives an Escape and is then deleted by the next Delete. That is what notes and dividers used to be: notes had no selection at all, and a divider had a single `App.selectedDividerId` that no marquee, select-all or Delete-with-a-state-selected knew about. `pickObject(set, id, multi)` is the shared click rule (shift/ctrl toggles; a plain click on something unselected replaces the selection; a plain click on something already selected keeps it, so a drag can start from any member), and `beginSelectionDrag(pt)` captures offsets for all three movable kinds at once so one gesture moves the whole selection whichever member it started on. Adding a selectable kind means a set, a `sync*SelectionClasses()` that repaints its class from that set, and entries in `clearSelection` / `selectAllStates` / the Delete branch — not a second selection model.

Dividers and notes take their undo point on the first *movement* (`App.dragPendingSnapshot`), the way states always did; pressing one is a selection, not an edit. `removeNotes`/`removeDividers` delete without snapshotting so that Delete over a mixed selection costs exactly one history step.

### The label kernel

**The innermost loop of the label stage is compiled, and the flattening above is what made that possible rather than the other way round.** `labelPenalty` answers how much trouble a candidate label box is in, by asking all three grids what is near it; after the grid work above it was still **33.6%** of the layout pass's JS time, with most of `gridQuery`'s remaining 15.9% called from inside it. [wasm/label-penalty.ts](wasm/label-penalty.ts) is that function and the grid it queries, in AssemblyScript; `npm run wasm` compiles it and writes it into [js/wasm/](js/wasm/) as base64, the committed-output arrangement [scripts/build-glyphs.mjs](scripts/build-glyphs.mjs) already uses.

**WebAssembly cannot see a JS object**, so every number the kernel reads had to be in a flat buffer before a kernel could exist at all — which is why the typed-array work came first and is not a detour. It is also, by a wide margin, the larger half of the win, and the two were measured separately because only one of them can be A/B'd in a single process:

| | | |
| --- | --- | --- |
| the grid and the flattening | **~2.0×** on the pass (10.0ms → 5.1ms at 200 states, 67 → 32 at 1000) | swapping the whole file, alternating runs |
| the kernel on top | **1.09–1.15×** (3.46 → 3.00ms at 200, 27.3 → 24.5 at 1000; a drag frame 1.66 → 1.46) | `setLabelKernel`, both kernels in one process, best of five |

On the function alone wasm is **1.39×** (586ns → 423ns per call), and it is ~45% of the pass, which is where the ~1.13× comes from. The lesson is worth keeping: against *well-written typed-array* JS the instruction set is worth about forty per cent, and the 2.9× that was really available here was a data-layout problem wearing a wasm-shaped hat. A JS→wasm call costs **6.2ns**, so batching the candidates into one call per label — the obvious next move — would buy nothing; the 1.39× is the kernel, not the boundary.

Points worth keeping in mind:

- **It is instantiated synchronously, and that is what dictates the delivery.** `buildLayoutContext` runs inside a frame — `updateFastDOM` calls it sixty times a second — so it can await nothing, which rules out `instantiateStreaming` off a URL. The bytes are base64 in a module the bundler already has, and `new WebAssembly.Module(bytes)` compiles them at module scope. **Chrome refuses synchronous compilation past 4KB on the main thread**; the kernel is 3,440 bytes and `scripts/build-wasm.mjs` warns when a change crosses the line. But that limit belongs to the browser, so it is *handled* rather than relied on.
- **Every way it can fail ends in `null`**, and [js/label-wasm.js](js/label-wasm.js) is the only module that knows about any of them: the size limit, a CSP forbidding `wasm-eval`, an engine with no `WebAssembly`, a corrupt artifact. `geometry.js` keeps the JS implementation of all of it for that case.
- **So the JS twin is not dead code, and it is not a degraded mode — it is the same diagram computed the other way.** That is the one thing about this that must not rot, so `setLabelKernel('js')` is a real seam and [tests/label-penalty-wasm.test.js](tests/label-penalty-wasm.test.js) uses it to lay the same machines out both ways and compare **every label position exactly**, on the full pass and across eight frames of a drag. Exactly, not approximately: a position is a sum of f64 penalties, and two kernels that only nearly agreed would come apart over a gesture rather than at the first frame. The harness restores `'auto'` in `resetModuleState`, or one test forcing the fallback would quietly hand it to the rest of the suite.
- **`Math.hypot` became `Math.sqrt(dx*dx + dy*dy)` on both sides**, because there is no hypot instruction to match it with. What hypot buys is protection against overflow at magnitudes a canvas coordinate never reaches, at a cost of a couple of ulp on a value that is then weighted and summed — so the two can be bit-identical, which is the property the test rests on.
- **The kernel owns the sample grid outright and only mirrors the other two.** Samples are by far the most numerous thing in a pass, so building that grid on both sides would cost more than the kernel saves; nodes and labels are wanted in JS as well — `nodesNearChord` and `chooseSelfLoopAngle` query the node grid, and `relayout`'s dirty scan asks the label grid which edge each box belongs to — and both are small enough that a mirror beats an export to read them back through.
- **It holds one pass's grids at a time**, which is safe only because `labelPenalty` is called from inside the pass that filled them and never from a context handed back to a caller. In `relayout` the reset therefore lands *after* the dirty scan, which reads the previous pass's JS label grid.
- **A group's key is an integer here.** `p.key !== ownKey` was a string compare, and it is the innermost comparison in the whole pass — run per sample, per candidate, per label. The id is the group's index in `ctx.groups`, stamped onto the geo where it is sampled, so a geo carried forward from the previous pass is renumbered against the grouping in front of it.



### The benchmark

`npm run bench` ([bench/run.mjs](bench/run.mjs)) measures the app's own code — `js/machines/**` and the renderer, loaded through `tests/harness.js` exactly as the tests load them — and compares the run with [bench/baseline.json](bench/baseline.json). 63 cases in six suites ([bench/cases.mjs](bench/cases.mjs)):

| suite | what it answers |
| --- | --- |
| `decide` | the cost per symbol or step of `decideMachine` on every finite, weighted, ω and tape machine: synthetic machines at chosen sizes (a DFA of 10 states against 100,000, 2 symbols against 200) and the bundled examples on input they are meant for. Includes the first 2M steps of the five-state busy beaver champion. |
| `search` | the configuration searches and two-way heads: DPDA, NPDA, Counter, PDT, FST, 2PDA, QA, EPDA, 2DFA, 2NFA, 2DFT |
| `tokenize` | reading 100k symbols typed with and without separators |
| `player` | `traceMachine` per step — the stream ⏭ drains, without the paint — and scrubbing across half of a 1M-step run |
| `memory` | the bytes a finished run keeps alive per step: the number the checkpointed player is meant to cut |
| `layout` | the JavaScript half of a canvas frame against the test DOM: first render, idle re-render, drag frame, full layout pass, at 200 and 1000 states. None of the browser's style, layout or paint is in it, and 1000 states is past the collision budget, so it runs under the large-machine profile. |

What it is built to get right, each learned from it getting it wrong first:

- **Every case records a check** — a verdict, a step count — beside its time, and the comparison marks a changed check whatever the timing did. A faster engine giving a different answer is caught, not celebrated. Flipping the DFA's verdict was marked `CHECK CHANGED` on a case whose time had not moved past its noise.
- **Most of the noise is between processes.** Two processes running the same code disagree by more than the repetitions inside one process do — each makes its own compilation and heap decisions — so an unchanged tree was once marked 82% slower on one case. Each suite therefore runs in `--rounds` separate processes (three by default, alternating the order), a case keeps its fastest median, and its spread is the larger of the within-run spread and the rounds' disagreement. A case is marked only when it moved by more than 1.5× that spread, and never by less than 10%. Two reruns of an unchanged tree mark nothing; reverting the DFA to the uncached per-step lookup marked four of the five DFA cases slower (+86% to +286%).
- **The heap is collected once before a case is timed, not before every run.** Collecting before every run looked steadier and was wrong: after a full collection V8 shrinks its young generation, the next run pays to grow it back, and allocating cases — the NPDA search, a drag frame — measured up to 1.7× slower than any real run is.
- **Memory is measured between two forced collections** and needs `--expose-gc`, which the suite processes are given.
- **Everything is seeded**, so a run builds the machines and words the last one did. A case that needs the whole run lifts the budgets (`maxPdaSteps`, `maxTmSteps`) out of the way, since the question is how long the work takes, not where the budget cuts it.

It is run by hand. A baseline is comparable only on the machine that recorded it, so it carries that machine's CPU and the report says when the two differ; record your own with `npm run bench -- --save`. `--quick` is one round of fewer repetitions, a filter word narrows the run (`npm run bench -- npda player`), `--out` writes a run to a file and `--baseline` compares against one.

### The engine's hot paths

**A step costs the same on a machine of any size**, and it took the changes below for that to be true. Measured before (in Node, the real `js/machines/**` through the harness): a DFA step cost 135ns on 20 transitions and 39µs on 10,000; the NPDA search and the tape deciders were quadratic in their own work on top of that. Each fix was pinned against a reference copy of the code it replaced in [tests/engine-speed.test.js](tests/engine-speed.test.js) — same answers, not merely plausible ones.

- **δ is indexed by source state.** `transitionsFrom(state)` in [js/machines/runtime.js](js/machines/runtime.js) replaced every per-step `App.transitions.filter(t => t.from === s && …)`, in δ's own order so a nondeterministic search still meets branches in the same order. The key is `from` *only*: the symbol, pop, tape symbols and target are read live, so editing them in place cannot stale the index. It validates itself like `stateIndex` (array, length, both ends) and the two places that rewrite `from` in place — the edit dialog and `ctxReverseTrans` — call `invalidateTransitionIndex()`. **A new simulator must not filter `App.transitions` per step**; ask `transitionsFrom`. 5,000 states / 10,000 transitions, 10,000 symbols: DFA decide 392ms → 2.2ms, NFA 781ms → 3.8ms, TM playback 636ms → 13ms.
- **The tokenizer is a table.** `splitSegment` asks "can the rest be split from here?" once per position, right to left, and walks forward taking the first symbol (longest first) that leads somewhere splittable — step for step the choice the old backtracking recursion made, without the recursion (which overflowed past ~10k undelimited symbols) or its `[s, ...rest]` copies (quadratic).
- **Breadth-first searches use `Fifo`**, amortized O(1) `shift`, where `Array#shift` was O(frontier) per configuration. The NPDA explorer narrates only the first `NPDA_LOG_KEEP` branches (its one reader, the algorithms card, shows ten) and `testNPDA` asks for no narration and no witness path — formatting an instantaneous description per configuration was the most expensive thing a search did.
- **The deterministic tape machines detect loops by fingerprint.** `Tape#trackFingerprint()` keeps a two-modulus polynomial hash of the non-blank cells, normalised to `key()`'s window edge so it is exactly as origin-independent as `key()` — a configuration that recurs *shifted* on a two-way tape is still a repeat. The hash is kept relative to the edge it was last normalised to (`fp.lo`), so reading it costs nothing until the edge moves, and a write adds one combined delta — nothing at all when it puts back the symbol that was there. `fingerprintParts()` hands it over as three integers, and `makeFingerprintTable` keeps them with the numbered state in a `ConfigSet` rather than a Map of strings. A fingerprint match is confirmed by replaying the deterministic run to the earlier step and comparing real keys (`makeRepeatDetector`, `seenAtVerified`), so a loop verdict is the one `key()` reached. `testTM3`, `testLBA3`, `testMTM3` and the three streaming players use it.
- **A deterministic run resolves each state's row of δ once.** `singleTapeLookup()` reads a state's edges into a row the first time the run is in it — per symbol the edge that wins, plus the wildcard edge — so a step is two Map lookups however many edges leave the state; `multiTapeLookup()` does the same per (state, symbols read). Rows outlive a run only on proof: filed under the index's own edge list (a WeakMap, so a rebuilt index takes them with it) and reused after checking each edge's symbol and id, which catches an edge edited in place with nothing announcing it. That check touches every edge once per run, so on a state with hundreds of edges a *short* run still pays about what reading the row cost — it is the price of noticing unannounced edits, and there is no cheaper proof.
- **A pushdown search's stacks are interned nodes.** `stackRoot()`/`stackPush()` in [js/machines/step-log.js](js/machines/step-log.js) make a stack a cons node whose children are shared per symbol, so a move builds O(|push|) nodes and equal stacks *are* one node — `node.id` names the contents exactly. Every search stack (DPDA, NPDA, Counter, 2PDA, PDT) lives there; the EPDA's store is a stack of such stacks, interned the same way; the queue automaton keeps its arrays, because a queue is taken from one end and added to at the other and no shared-tail structure makes both O(1) while keeping equal queues equal. A step holds `stackRef`/`storeRef` and spells `stack`/`stack2`/`store` out when read (`pdaStep`, `epdaStep`). The visited set is a `ConfigSet` — five int32s a slot in one typed array, exact, no string per configuration — with the state numbered per search (`makeStateNumbering`), and `pdaMatcher()` remembers which moves apply per (state, next symbol, top) for the length of a search. NPDA ww^R on a^500b: 238ms → 21ms, and linear in the configurations where it was quadratic.
- **A transducer's output joins its key as a node, not as the string.** `outputKeyAfter(node, piece)` pushes the output a character at a time onto an interned trie, so "a" then "b" and "ab" at once reach the same node, and the PDT and FST visited sets key on its id. Keyed on the string, a configuration cost the whole output so far: the PDT reversing a 2,000-symbol word exhausted a 4 GB heap; at 800 symbols it went 3.9s → 0.18s.
- **An NFA's state set is integers.** `NfaSets` in [js/machines/finite.js](js/machines/finite.js) numbers states on first sight, remembers each state's targets per symbol and its ε-edges for the run, and marks membership with a stamp array, so a step allocates one list and hashes nothing. It builds the set in exactly the order the Set version did — direct targets in δ's order, then the ε-closure depth first — because the trace prints it. 1,024 states: 240µs → 44µs a symbol.
- **The NDTM search forks a zipper.** [js/machines/zipper-tape.js](js/machines/zipper-tape.js) is the tape as two interned stacks either side of the head cell: a fork is O(1) where `Tape#clone` copied every cell, and a configuration is (state, left id, head symbol, right id) in a `ConfigSet` where it was the tape spelled out. The stacks are trimmed to exactly `key()`'s window, which `tests/engine-speed.test.js` checks against `Tape` operation by operation. A word containing the blank keeps `Tape`: there a written blank and an unwritten cell differ at the window's left edge, and a zipper that trims blanks cannot see it. The streamed search's steps keep their configuration's tape and spell it out when read (`NDTM_STEP`). The example at n = 60: decide 346ms → 22ms, trace 800ms → 126ms.
- **A streamed step formats its note only if it is read.** The hot streams pass the note as a function (the argument after the step's fields: `wordStep(props, noteOf)`, `tapeStep(log, i, fields, noteOf)`), and the step's prototype variant (`lazyNoteProto`) calls it on first read and keeps the string; `step.note += …` still works. The note was a third of a streamed step's cost for a line the trace log shows only for its last screenful. It must capture the step's own values — the loop's variables have moved on by the time anyone reads it.
- `Tape#snapshot()` walks the cells for its ends rather than spreading them into `Math.min`/`Math.max`, which throws past ~100k arguments.
