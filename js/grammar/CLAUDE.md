
### The grammar workbench

The Grammar view. **A grammar is written once and then taken apart by ~25 tools**, laid out the way the Algorithms and Reference views are: a generated nav rail beside a content pane. What is particular to it is where the grammar sits — in a sticky card at the *top of the content pane* rather than in the rail, because a result is only readable beside the rules that produced it, and it folds to its own footer strip when a CYK table or a parse tree wants the room.

```
js/grammar/
  registry.js    import-free. defineTool / defineGroup, and the nav lookups.
  parse.js       import-free, App-free. Text -> rules + diagnostics.
  model.js       the model, and the only seam to App.grammar.
  analysis.js    nullable / generating / reachable / FIRST / FOLLOW /
                 left recursion / classification. Pure.
  transform.js   ε-removal, unit, useless, CNF, GNF, left recursion,
                 left factoring. Each answers a worked construction.
  parsing.js     CYK, parse trees, derivations, ambiguity, LL(1),
                 word generation.
  tree.js        import-free. Parse-tree layout — geometry only.
  convert.js     CFG <-> PDA, regular grammar <-> finite automaton.
  blocks.js      import-free. The result vocabulary.
  examples.js    import-free. The library.
  tools.js       one defineTool per thing the workbench does.
js/grammar-ui.js the only DOM-bound module: blocks -> nodes.
```

**A tool computes and the view writes, and that is the property the whole thing is arranged around.** `run(ctx)` is a pure function of the grammar and the reader's inputs, answering with blocks — it never reaches for `$`, never writes HTML and never mutates anything. Applying a result to the editor is an *action* the view performs, so a tool that throws, or one whose answer the reader simply reads and moves on from, leaves the grammar and the canvas exactly as they were. That is the same "written exactly once, at the end, or not at all" invariant the wizard and StateMate hold.

It is also what the old view could not do. Each of its eighteen buttons read `$('gram-output')` and wrote a string of HTML, so nothing it computed could be asserted on without a document — and four of its algorithms were quietly wrong for want of a test that looked at the value rather than at the markup:

- **`runGNF` did not convert.** It printed which rules already began with a terminal and stopped, under a note calling itself a "simplified pedagogical version".
- **The derivations chose their productions at random** (`prods[Math.floor(Math.random() * …)]`), so they were derivations of nothing in particular and gave a different answer on each press.
- **`runParseTree` always took `prods[0]`**, so it drew a tree for an arbitrary word rather than the one you typed.
- **`runChomskyClassify` collapsed Type 0 and Type 1** into one bucket and never tested the non-contracting condition, so a context-sensitive grammar and an unrestricted one were reported identically.

Points worth keeping in mind:

- **`registry.js`, `parse.js`, `tree.js`, `blocks.js` and `examples.js` import nothing**, for the reason [js/machines/registry.js](js/machines/registry.js) does: `tools.js` calls `defineTool` at module scope, and a shared mutable container written at module scope has to sit in a leaf.
- **The parser's tokenization is declared, not guessed, and that is the whole reason it exists.** The old `tokenizeRHS` matched right-hand sides against a variable set it was filling *in the same loop*, so `S → AB` above `AB → a` meant two symbols and below it meant one — a grammar whose meaning changed when you reordered its rules. The rule now, in order: a bracket form (`[q0,A,q1]`, `<Expr>`) is always one symbol; whitespace separates symbols wherever it appears, which is how a context-sensitive left-hand side is written; and inside a whitespace-free run the longest symbol in the known vocabulary wins, with single characters as the fallback. **The vocabulary is complete before any right-hand side is read**, because it comes from a full first pass over the left-hand sides — and a left-hand side is tokenized against the whitespace-free left-hand sides alone, so it has no dependency on the rules below it either.
- **V is not every symbol that appears on a left-hand side**, and reading it that way is what broke the one grammar in the library that is not context-free. A Type 1 left-hand side is αAβ where α and β are ordinarily *terminals* — `a B → a b` says B may be rewritten after an a, and nothing about a — so counting them all put `a`, `b` and `c` into V for `aⁿbⁿcⁿ`, which left Σ(G) **empty**: the Rules view coloured its terminals as variables, the footer read `V 6 Σ 0`, and every word tool refused the example's own declared test words as symbols the grammar had never heard of. A symbol earns V structurally where the text says so — standing as a whole left-hand side, or being a bracket form — and inside a longer left-hand side there is no structural signal left, so the reader's convention is all there is to read: an initial capital, announced as a diagnostic the way the terminal rule below is. **`deriveVars` is exported from `parse.js` because `readGrammar` has to reach the same answer from the persisted productions** — written twice, the editor and the reload disagreed about V, and since `readGrammar` runs on every render it was the *reload's* answer the view showed.
- **A multi-character alphanumeric run containing no declared variable is one terminal**, so `F → ( E ) | id` is a grammar over `{(, ), id}` rather than one over `{i, d}` that nobody wrote. The rule can still be wrong — `S → a S b | ab` gets one terminal `ab` — so it is *announced* as a diagnostic rather than applied silently, and writing `a b` is how you say the other thing. The Rules view exists for the same reason: it shows what the parser actually read.
- **Diagnostics are keyed to the field, not to focus.** They carry line numbers, and the editor is only overwritten when what it holds no longer describes the grammar the workspace has — a load, an undo, an Apply. Deciding that on `document.activeElement` instead, which is the obvious way, meant a malformed line stopped being reported the instant the field lost focus and was then erased by the canonical text on the next render.
- **The start symbol is a `<select>` over V.** It used to be a free-text input in a third place, happily naming a variable the grammar did not have — after which every tool answered about a start symbol that derived nothing.
- **`App.grammar`'s persisted shape is unchanged.** It is still `{vars, start, productions:[{lhs, rhs, rhsArr}]}`, which the `.json`, the share link, the PNG payload and the undo stack all carry; a rule is a superset of a production, so `readGrammar` is a normalization and `writeGrammar` a projection. No migration, and a file written by an older build opens unchanged. `writeGrammar` assigns a plain `Set` to `vars` on purpose — state.js's coercing accessor upgrades it, and going around that installs a field that stops notifying with no error anywhere.
- **`Change.GRAMMAR` is its own kind**, for both of the reasons `META` is: it is persisted, so it dirties the tab; and it is not the machine, so it must not drag the diagram, the panels and the formal definition through a re-render because a production was retyped — which is what emitting `GRAPH` on every keystroke would do. **And every path that rehydrates `App` has to announce it**, exactly as they all have to announce `META`: `switchTab` and `createTab` in `ui.js`, `loadData`, `resetWorkspace`, `restoreSnapshot` and StateMate's `restoreCheckpoint`. Left out of one, the editor goes on showing the grammar of whatever was open before — and the next keystroke writes that grammar into the workspace it is now sitting in front of.
- **The grammar is on the undo stack, and a run of keystrokes is one entry.** `serializeState` carries it beside `App.meta` for the same reason: it is part of what `getWorkspaceData` saves, so one Ctrl+Z has to take back a retyped rule the way it takes back a dragged state. An entry there is the whole workspace as JSON, so `commit()` per character both stringified the machine on every keypress and buried the reader's last canvas edit sixty presses deep — and on a large machine the byte cap then evicted it outright. `commitTyping` coalesces a run; the run is ended by the clock **or** by `App.history.length` moving, since an undo, a redo or any other edit landing between two keystrokes means folding them would join two different edits into one entry.
- **The result pane's frame is built once per tool, and only the part below it is replaced.** A render runs on every keystroke — including the keystrokes going into the tool's own word field — and an `innerHTML` write over the pane removes that field from the document, which takes the focus and the caret with it: each word field accepted exactly one character and then went dead. It is also what keeps the symbol-suggest popover anchored to a field that is still the element it was attached to. A reused frame has its fields written back from `inputs`, guarded on inequality so the write cannot land during typing.
- **`needs: { word: true }` is a real gate, and `unmet` is where it is made.** `tokenizeWord` refuses a word it cannot read rather than splitting it into characters — which is what lets a tool name the unknown symbol — and the refusal carries no `tokens`. A tool reading `word.tokens` without checking therefore threw, and a half-typed word is in exactly that state on *every keystroke*: typing `i` into the expression grammar's word field showed an internal error. `ll1` deliberately declares no `needs.word`, because its table is about the grammar and stands whatever was typed; it reports the unreadable word and draws the table anyway.
- **Two engines, and the split is deliberate.** CYK decides membership: cubic, total, defined on Chomsky normal form, so it always answers and the table on screen is a table of the *converted* grammar. Everything a reader *reads* — a derivation, a tree, an ambiguity witness — has to be about the grammar they wrote, so those come from a separate top-down search over the original rules, which CYK gates: the search only ever runs on a word already known to be in the language, which is what keeps its worst case off the screen. A CNF parse tree is binary and full of `X₁` and `T_a` and shares no shape with the one in the textbook.
- **A leftmost and a rightmost derivation are two readings of one tree**, which is why `derivationOf` takes an order rather than there being two searches. Cycles are cut on the (symbol, span) being expanded: a derivation that re-enters the same symbol over the same span could be repeated forever, so there are infinitely many of them and none is a witness to anything.
- **Every transform states what it assumed.** GNF needs Chomsky normal form and left-recursion removal needs ε-rules gone; both establish the precondition themselves and say so in `notes`, because silently doing either is how a reader ends up with a correct answer to a question they did not ask. `stages` is the worked construction, one entry per textbook step *with the grammar it left behind* — which is what the view scrubs and what a test asserts on.
- **Left-recursion removal does the indirect kind**, which is the case with no rule that looks recursive: `A → B a, B → A b`. Fixing an order on the variables and substituting each earlier one out is what turns every indirect cycle into a direct one first. A variable whose every alternative is left-recursive is left alone and the reason given — there is no non-recursive alternative to anchor the rewrite on, so rewriting would change the language rather than preserve it.
- **GNF's left-recursion step is the ε-free variant** (`A → β | β A'` rather than `A → β A'` with `A' → ε`), because an ε-rule on a variable that is not the start symbol is exactly what Greibach normal form forbids — the ε form leaves the construction one rule short of its own definition. It then prunes: the terminal variables CNF introduced are unreachable once the terminals are written literally, and leaving them in triples the size of the answer with rules nothing can use.
- **Nothing here is reached from an `on*` attribute.** Listeners are attached at creation, the way `reference.js` and `machine-card.js` do it, so the view removed **twenty** names from [js/bridge.js](js/bridge.js) and added none.

[tests/grammar-workbench.test.js](tests/grammar-workbench.test.js) pins that no tool writes to `App`, that every block kind a tool emits has a renderer case, that the bridge stayed empty, and that the rail's id agrees across the markup and the three places `js/ui.js` names it — a mobile sheet whose id no longer matches an element is silent, so it simply opens over the view and never closes. [tests/grammar-view.test.js](tests/grammar-view.test.js) drives the view itself: that the editor and `App.grammar` are the same grammar in both directions, that a typing run costs one undo entry and one undo takes it back, that a keystroke does not rebuild the field it went into, and that a word the grammar cannot read is stated rather than thrown.
